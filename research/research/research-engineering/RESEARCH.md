# 科研工程中的协议保真、实验运行与可恢复结果

科研工程负责将已确定的研究方法转化成真实代码、运行配置和可追溯的实验结果。工程上“程序运行成功”与科学上“实验按计划执行”是两项不同的判断。一个系统即使通过编译并输出成功率，也可能因为数据版本、模型输入或失败排除规则发生变化，而不再测量原定研究问题。

这类问题在大规模 LLM 研究中尤为明显。模型调用有成本与不确定性，实验可能因网络、配额或环境中断；一个任务会产生多个候选，多个任务又可能并行。没有稳定的运行身份和失败记录，就难以知道正式结果到底对应哪套代码、哪次评估以及哪些未完成任务。

## 一、先定义需要保真的科学语义

科学协议至少包含任务对象、核心机制、数据划分、模型可见信息、Baseline、评价指标以及失败和预算规则。工程实现时，应能将每一项定位到实际源码、配置键、数据文件或自动化检查。若某个理论步骤没有实现，或者脚本无意中允许模型读取参考答案，研究主张可能已经发生实质变化。

举例来说，自动软件修复的方案可能要求针对同一 Issue 生成多组候选补丁并筛选。把多次候选减少为一次，既可能降低成本也可能降低成功率，这种工程改变直接影响科研比较，不应作为“仅提高运行效率的优化”静默合入。与之不同，修复不改变输入、候选分布、评价逻辑的日志格式问题，通常可以视为工程维护。

当论文、作者公开代码和本地实验计划不一致时，不应自行组合成一个“可能更合理”的实现。首先应定位冲突版本，明确哪份材料定义当前复现目标，再决定是否记录偏差或开展独立的新配置实验。

## 二、Agentless 案例中的流程与采样身份

[Agentless（FSE 2025）](https://lingming.cs.illinois.edu/publications/fse2025.pdf) 将仓库级自动修复组织为定位、修复与补丁选择三个阶段。其 [v1.5.0 代码仓库](https://github.com/OpenAutoCoder/Agentless/tree/v1.5.0) 的 `README_swebench.md` 给出实验入口，`agentless/repair/rerank.py` 与 `agentless/test/generate_reproduction_tests.py` 分别涉及候选排序和复现测试生成等具体程序环节。

这一研究适合解释实验身份为什么重要。论文与对应配置中的候选补丁数量和候选位置分组属于正式实验条件。例如部分设置按四组编辑位置、每组十个补丁生成 40 个候选；如果为了节省时间把候选数改成 10，即使后续仍运行相同的补丁筛选脚本，最终输出也属于不同实验协议。

在实际项目中应将修复任务的唯一 ID、候选组配置、模型版本、随机性设置、代码提交、测试基线与最终选择结果关联起来。若原始结果只保存“此题修复成功”，后续分析者无法检查成功是否来自改变了候选数、使用了不同测试，或者误把开发 Pilot 计入正式结果。

## 三、验证层级应对应不同风险

编译和静态检查可发现语法与配置问题；单元测试能检查局部函数；集成测试检验多个模块的数据交接；Pilot 则用于小规模验证整个实验链条、费用、失败处理和结果格式。正式评价需要进一步固定数据与协议，并按其定义生成实验结果。若研究依赖真实工具运行或人工验收，还需要相应来源明确的检查。

这几个层级不能互相代替。例如测试评估器代码通过单元测试，不意味着新生成的补丁确实解决了真实 Issue；模型输出符合预期 JSON 格式，也不意味着建议具有正确技术语义。科研工程需要设计有针对性的检查，而不是为了减少出错可能无限叠加形式相同的检查。

Pilot 使用开发样本或专门安排的先导样本，目的是验证流程、测量预算、确认指标实现和预先发现问题。正式运行之前应冻结主要参数及状态含义。若 Pilot 反复使用正式测试集选参，即使最终运行只出现一次，“正式集未被训练使用”的声明也可能不成立。

## 四、失败、超时与恢复也是实验数据

大规模实验常见的状态包括：未运行、执行中、成功、模型输出无效、真实测试失败、超时、基础设施中断和结果待人工核验。这些状态对分析结论影响不同。简单地把所有非成功输出删除，可能改变分母；把所有超时都当成模型功能错误，也可能混淆实验系统与目标方法的失败。

运行记录应在任务级绑定稳定身份：任务、方法、主要配置、代码/数据版本、尝试次数、输出位置、验证方式和终态。对于重复采样，需要将候选与同一任务关联，并保存候选状态，不能把多个候选当作多个独立评估任务。

重试的作用是从可恢复故障中继续，而不是重新抽取直到成功。临时网络故障可以在有限预算内重试；功能性失败或不符合协议的输出，需要按正式规则记录。程序恢复时应检查已有结果身份和有效性，避免同一个任务被重复计入，或因为版本变化继续错误地复用旧结果。

原子写入与幂等状态管理尤其适合长时间运行的任务：先写临时结果并确认完整，再更新最终状态；恢复时以任务和配置身份查找，而不是只看某个文件名是否存在。科学配置发生变化时，应使用新的结果身份，以免混合不兼容输出。

## 五、从运行成果交接到统计分析

实验工程的直接交付应包含实际代码、环境与配置、机器可读原始结果、运行状态和必要验证。交接给统计分析时，需明确计划多少任务、完成多少、失败与缺失多少、哪些属于可比配置、哪些验证级别已经达到。

如果研究者只得到一个成功率，无法知道未完成任务是否被排除、结果是否经过真实测试、模型费用是否在相同预算下计算，也无法进行可信的配对分析。因此结果存储和元数据不是可有可无的工程日志，而是科研证据链的一部分。

执行层可以报告哪些任务在实际测试下成功，却不应自行把程序运行解释为论文机制已被证明。机制和统计主张仍需要由实验分析检查其真实数据、比较协议和替代解释。

## 六、来源与研究边界

主要案例来自 [Agentless 论文（FSE 2025）](https://lingming.cs.illinois.edu/publications/fse2025.pdf)、[作者仓库 v1.5.0](https://github.com/OpenAutoCoder/Agentless/tree/v1.5.0) 及 [SWE-bench（ICLR 2024）](https://proceedings.iclr.cc/paper_files/paper/2024/file/edac78c3e300629acfe6cbe9ca88fb84-Paper-Conference.pdf)。这些案例提供具体工程与评价关系；它们不能自动成为任意研究实验必须使用的状态字段或候选数量。实际复现必须回到当次批准的版本、模型、配置与许可。本文讨论的是协议保真方法，并不表示运行了上述公开代码或复现作者结果。

## 七、研究结论如何形成 `research-engineering` Skill

[SKILL.md](../../../skills/research/research-engineering/SKILL.md) 以科学定义到代码的映射作为第一步，然后引入有界 Pilot、正式运行、任务身份与恢复，最后把真实结果交给实验分析。

| 研究认识 | Agent 的动作 | Skill 文件 |
| --- | --- | --- |
| 程序可运行不证明符合科学协议（第一节） | 建立机制、数据、Baseline、指标和失败规则的源码/配置对应 | [protocol-and-validation.md](../../../skills/research/research-engineering/references/protocol-and-validation.md) |
| 候选采样与执行参数是科学设置（第二节） | 检查采样数量、信息条件和运行版本，记录偏差并取得授权 | [protocol-and-validation.md](../../../skills/research/research-engineering/references/protocol-and-validation.md) |
| Pilot 和正式执行的证据层级不同（第三节） | 先测试运行链条，正式阶段冻结参数与数据，不混用结果 | [SKILL.md](../../../skills/research/research-engineering/SKILL.md) |
| 失败、重试和恢复影响分母和可比性（第四节） | 用稳定任务身份、有界重试和幂等写入保留全部终态 | [run-identity-and-recovery.md](../../../skills/research/research-engineering/references/run-identity-and-recovery.md) |
| 统计分析需要真实原始记录（第五节） | 交付任务级输出、配置、验证来源和未完成状态 | [run-identity-and-recovery.md](../../../skills/research/research-engineering/references/run-identity-and-recovery.md) |

Skill 保留工程工作者可以自主修复普通技术错误的空间，但科学定义、实验规模和评价规则由研究者批准。输出侧重真实代码和机器可读证据，不要求每次运行都产生单独研究报告。科学结论归 `experimental-analysis` 负责，使实现与解释之间保持可检查的界限。
