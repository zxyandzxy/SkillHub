# 研究数据集与 Benchmark 的构建：来源、任务有效性和信息隔离

研究数据资产的价值取决于它是否真实测量目标能力，以及使用者能否核查数据从哪里来、经过哪些转换、在什么条件下得到标签和评价结果。数据规模很大仍可能存在系统性偏差：一个自动生成的程序修复任务如果没有可靠失败复现，可能并不需要修复；一个包含真实答案的提示词可能使模型在评测时获得不应看到的信息。

Benchmark 构建既是数据工程，也是科学方法的一部分。研究者必须先定义目标任务和评测目标，再选择采集、过滤、标注与验证程序。已有公开数据可用时，复用与扩展通常比重新构造更可靠，但公开可用并不意味着当前研究可以任意加工或分发。

## 一、确定数据资产的研究职责

训练集、开发集、正式测试集、检索知识库、标注集和参考答案具有不同信息可见性。如果一个系统在正式测试时能够检索到包含目标补丁的历史数据，它获得的是一种不同于未知 Issue 修复的条件。决定数据划分之前，应明确每个资产在科学协议中承担的作用。

研究者还需区分数据资产是论文本身的贡献，还是帮助评价某个方法的支撑材料。若数据集是主要贡献，需要论证任务定义、覆盖、标注质量和社会或工程使用价值；若只是评价支撑，则必须说明数据对目标研究问题适用，并维护与既有方法可比的评价条件。

数据处理不应由“多少条足够发表”驱动。对软件修复任务，较少但可复现、语义明确的 Issue，可能比大量无法验证的自动生成实例提供更可信的证据。过滤规则应根据任务有效性确定，并解释过滤是否改变了研究总体。

## 二、SWE-bench 展示任务构建为何需要执行验证

[SWE-bench: Can Language Models Resolve Real-world GitHub Issues?（ICLR 2024）](https://proceedings.iclr.cc/paper_files/paper/2024/file/edac78c3e300629acfe6cbe9ca88fb84-Paper-Conference.pdf) 通过真实 GitHub Issue 与修复它的 Pull Request 构造任务。原始论文报告了来自 12 个 Python 仓库的 2,294 道任务。每题需要提供问题说明和对应仓库基线，并评估生成补丁是否让相关测试通过。

这个构建流程包含多道不能省略的判断。Issue 和 PR 的链接提供一个候选关联，但不自动证明两者的因果对应；PR 中新增的测试可能用于复现原始缺陷，也可能只是扩展回归覆盖。构建者需要核对仓库在指定基线能否安装、相应失败测试是否真实失败、修复后是否满足对应验证，以及任务是否缺少必要上下文。

例如一条 Issue 说“某 API 遇到空值时应保持原输出格式”，对应 PR 修改多个函数并新增测试。若采集只保存 PR 修改的代码片段，任务可能丢失调用方和项目依赖，无法真实复现；若把 PR 的修复代码提前提供给模型，任务又变成了带答案的实现。构建数据集必须精确记录原始仓库状态、输入可见范围和被隐藏的参考答案。

[SWE-bench Lite](https://www.swebench.com/original) 等子集通过不同筛选条件形成不同的研究对象，不应直接视作原始数据集的另一个名称。研究中使用哪个版本，需要明确到任务 ID 和评价环境。

## 三、标签和质量证据应对应任务类型

不同数据资产的“正确”含义不同。对于代码生成，语法和编译通过可以发现明显错误，但功能正确性需要能触及目标行为的执行测试；对于程序修复，需要检验初始状态、缺陷复现、候选补丁和回归约束之间的关系；对于主观人类标注，则需要清楚的标签指南、样本选择、独立判断和争议处理。

模型生成的答案尤其需要独立检查。让同一个模型反复判断自己生成的代码，可能暴露多个模型共享的错误理解。模型互相投票可用于安排人工复核优先级，但不能以“多数模型同意”替代可执行测试或专家审查。

对知识类资产，质量还包括来源权威性和时间有效性。例如公开 API 文档在不同版本中可能修改参数定义，一个知识库如果只记录网页片段而没有版本或更新时间，就难以解释模型产生的错误是否来自知识过期。对于自动合成的题目，还需要检查歧义、重复、答案可判定性和任务分布。

静态检查、自动执行、真实工具验证和人工审查应分开记录。得到“语法检查通过”只能说明语法层面符合要求，不能说整个数据集已获人工功能验收。

## 四、去重、数据泄漏与总体偏差

泄漏并不只发生在训练集和测试集文件名相同的情况下。同一 Issue 的多个 PR、仓库 Fork、不同版本代码、相似生成题以及评测时的检索结果都可能让测试信息进入模型可见范围。对于公开代码任务，还要考虑模型预训练阶段可能遇到原始答案这一不可完全排除的风险。明确测量假设并报告可能的污染，比假装所有测试任务全新更可靠。

过滤行为也会影响总体。例如移除缺少上下文、无法复现和含有误导信息的任务，可能提升评价可信度，但过滤后的 Benchmark 不再完全代表原先的任务分布。[Agentless（FSE 2025）](https://lingming.cs.illinois.edu/publications/fse2025.pdf) 对 SWE-bench Lite 任务进行了人工类型分析，并构建过滤后的 Lite-S，以研究已有基准中的不充分和误导性 Issue 描述。此类分析说明“题目原本来自真实世界”不能代替“题目目前适合测量所宣称能力”的验证。

数据质量报告需要同时给出保留、排除和不确定样本的数量、理由及分布，避免只公布保留集的漂亮统计。若某类仓库或语言因环境部署困难而被大量排除，则最终适用范围可能更窄，应在研究结论中说明。

## 五、许可与发布边界

技术可访问性和法律使用权限需要分别核查。公开 GitHub 代码可能附带不同许可证，Issue 还可能包含个人信息、内部链接或安全敏感内容。研究者应记录来源、取得方式、实际采用的条款，以及是否允许批量抓取、模型处理和再分发。内部允许用于论文实验也不能自动推导出允许公开整个数据副本。

公开发布时需要冻结版本、说明数据字段与变换、提供合理的重建步骤，并区分参考答案与测试时允许输入。受限制的原始材料可以保留合法的来源索引或经授权的匿名化版本，不应为了追求完整而上传未经许可的内容。

## 六、研究结论如何形成 `dataset-benchmark-engineering` Skill
