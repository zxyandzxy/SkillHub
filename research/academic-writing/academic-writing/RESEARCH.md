# 计算机科学研究论文的论证组织与学术写作

研究结果进入论文后，读者需要判断三个问题：研究解决了什么具体困难，提出的方法为何能够回应这个困难，以及实验是否充分支持作者的结论。论文的章节安排、技术说明和语言表达都应服务于这些判断。

计算机科学论文通常同时涉及算法或系统机制、实现条件、实验协议以及与已有工作的关系。即使每句话在语法上正确，读者仍可能因为缺少设计动机、关键定义或比较依据而无法理解贡献。写作过程因此需要同时检查**论证是否成立、技术信息是否完整、文字是否便于核查**。这三项要求也决定了哪些内容值得展开、哪些内容可以精简。

## 一、从研究成果到可核查的学术论证

### 研究主张需要证据和推理共同支撑

论文中的陈述可按性质区分为研究事实、实验观察与作者解释。研究事实包括任务定义、已有方法的机制和引文所支持的结论；实验观察包括在具体数据、模型和评价协议下得到的数值与现象；作者解释则进一步说明现象的可能原因、适用条件及其意义。

这几类陈述需要不同的支撑方式。描述已有工作的局限，应引用最相关论文或给出可核对的实例。报告性能差异，应明确比较对象、样本、指标与配置。解释差异由某一机制导致，则需要消融、对照实验或其他能够排除替代解释的证据。读者应能够沿着正文找到每项重要判断的依据。

例如，在仓库级软件修复研究中，作者可能观察到增加某种候选补丁筛选机制后，最终成功修复的问题数上升。这个观察可以支持“所测试配置中的补丁选择效果改善”。若进一步声称筛选器能稳定识别某类错误补丁，就需要查看逐任务筛选记录，检验它实际排除了什么、保留了什么。总成功数本身不足以完成这种机制分析。

### 论证需要回答连续的问题

一个方法类研究通常存在如下关系：

`实际任务及限制 → 现有研究能解决的部分与剩余问题 → 方法设计的依据 → 可检验的研究问题 → 实验观察 → 允许得出的结论`

这条关系是检查论证完整性的工具，各部分在正式论文中的顺序可以根据研究类型调整。重点在于相邻部分之间存在可解释的推导。例如，前文声称现有方法缺少某类信息，方法部分应说明如何获得并使用该信息，评价部分则应检验它是否带来预期作用。

当某个连接缺少依据时，有三种合理处理：补充已有且可验证的证据，收窄主张，或者明确指出尚待验证。语言润色无法替代这个判断。研究者也应区分“相关工作没有采用相同结构”与“相关工作无法解决相同问题”，后者需要更具体的比较。

## 二、从真实论文观察不同的论证路径

论文类型与研究问题不同，建立动机的方式也会不同。以下四项公开研究说明了几种能够具体分析的写作路径。

### MultiPL-T：用数据问题和验证机制连接研究动机

*[Knowledge Transfer from High-Resource to Low-Resource Programming Languages for Code LLMs](https://doi.org/10.1145/3689735)*（OOPSLA 2024）研究代码语言模型在低资源编程语言上的适用性。问题与可用训练数据密切相关：高资源语言包含较多代码和测试材料，低资源语言的数据规模与质量则限制了直接训练和迁移的选择。

MultiPL-T 的方法围绕训练数据的可靠性展开：先为源语言程序生成测试并筛除不可靠样本，再将程序转换为目标语言，随后利用测试验证过滤错误转换。这里值得关注的论证关系是，作者需要说明合成数据为什么可能帮助低资源语言，以及未经检查的转换为何会损害训练材料的质量；测试和过滤环节因此具有具体的设计理由。

当一个研究存在若干看似可行的替代方案时，这种论证方式尤其有效。作者可以先说明替代方案在目标条件下能够做什么，再通过数据、机制分析或实验说明尚未解决的困难，最终解释新方法中的关键步骤为何必要。替代方案的数量由实际问题决定，无需人为凑出固定数目。

### Code Search Is All You Need：从开发任务收窄研究问题

*[Code Search Is All You Need? Improving Code Suggestions with Code Search](https://doi.org/10.1145/3597503.3639085)*（ICSE 2024）围绕代码补全与代码生成中的检索增强展开。论文从开发环境提供代码建议的实际任务出发，讨论如何使用检索得到的代码片段改善语言模型的建议结果，并比较不同检索和搜索策略。

这类论文的背景介绍应尽快回答：代码建议发生在什么场景，模型在这个场景中需要哪些信息，已有检索手段留下了什么值得研究的问题。给出这些条件后，读者可以理解检索策略为何是主要研究变量，也能判断实验是否覆盖相应任务。

可迁移的写作经验是用具体工作场景限制问题范围。技术背景的长短取决于理解后续方法所需的知识量。对熟悉代码补全任务的读者，重复介绍整个大模型发展史并不会增加论证信息。

### AllianceCoder：让初步研究决定方法设计

*[What to Retrieve for Effective Retrieval-Augmented Code Generation? An Empirical Study and Beyond](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/182/What-to-Retrieve-for-Effective-Retrieval-Augmented-Code-Generation-An-Empirical-Stud)*（ICSE 2026）首先比较仓库级代码生成中的不同信息来源，包括上下文代码、潜在 API 信息和相似代码片段。论文报告，这些信息的作用并不相同；相似代码检索在所研究的部分设置中还可能引入噪声。作者据此提出 AllianceCoder，使检索和生成机制回应前面的实证观察。

这条路径适用于“缺少哪种信息、何种信息真正有效”尚未清楚的研究。初步实验为后续设计提供理由，方法章节再说明每个机制如何处理对应观察。写作时需要保留初步研究的模型、数据与任务条件，以免把局部发现写成对所有检索系统都成立的结论。

### ArkAnalyzer：领域差异可以构成工程研究的动机

*[ArkAnalyzer: The Static Analysis Framework for OpenHarmony](https://doi.org/10.1109/ICSE-SEIP66354.2025.00018)*（ICSE 2025 SEIP）研究面向 ArkTS 和 OpenHarmony 应用的静态分析框架。论文指出，ArkTS 与 TypeScript 之间的语法及抽象语法树差异，会使既有 JavaScript/TypeScript 分析工具在处理 ArkTS 代码时遇到具体障碍。框架的设计动机来自这些语言与工具层面的不兼容问题。

在系统工具论文中，领域约束往往需要具体到语法结构、接口、数据流或执行环境。只有交代这些差异，读者才能判断现有工具为什么难以直接复用，以及新框架必须支持哪些能力。ArkAnalyzer 属于 SEIP 论文，其叙述重点不能直接决定研究型论文的章节结构；可以借鉴的是将技术差异转化为可检查的工程需求。

这四种路径分别强调数据与替代方案、实际工作场景、初步实证发现和领域工具约束。共同点是方法的设计理由可以追溯到明确的问题及证据。写作者需要选择符合自身研究性质的论证方式，保持研究逻辑完整，而不复制范例的段落数量、句式或章节标题。

## 三、章节与段落怎样承担论证职责

章节划分首先取决于读者在何处需要什么信息。不同会议和论文类型允许合并或调整章节；相同标题下也可能承载不同的技术深度。

| 常见部分 | 需要解决的读者问题 | 容易遗漏的必要信息 |
| --- | --- | --- |
| Abstract | 研究了什么问题，如何解决，最重要的证据是什么？ | 任务条件、主要结果的实际含义 |
| Introduction | 为什么值得解决这个具体问题，现有工作留下了什么空间？ | 真实问题证据、最近方案的实质差异 |
| Background / Motivation | 理解研究机制需要哪些知识？ | 定义、贯穿的具体例子、失败条件 |
| Related Work | 本研究相对于最相关方法处于什么位置？ | 统一比较维度、相关工作适用范围 |
| Method / Approach | 方法如何工作，为什么采取这些设计？ | 输入输出、关键算法、状态、参数与假设 |
| Experimental Setup | 为什么这些比较能够检验研究主张？ | 数据版本、Baseline、指标、控制条件 |
| Results | 每个研究问题获得了什么答案？ | 关键差异、分母、变化幅度和不确定性 |
| Discussion | 各项结果共同说明什么，如何理解反常发现？ | 机制解释的证据、实际意义和代价 |
| Threats to Validity | 哪些条件限制对结果的解释与推广？ | 重要威胁、已有缓解措施和剩余影响 |
| Conclusion | 读者应当保留哪些经过支持的认识？ | 与贡献对应的结果、适用范围 |

### Related Work 应围绕比较问题组织

如果两项研究都使用代码检索，单独介绍它们各自的模型结构还不足以完成定位。更有效的比较会明确检索对象、可访问的信息、生成任务、评价条件，以及每种机制能够处理的困难。

例如，Code Search 研究代码建议中的检索增强，AllianceCoder 则进一步区分仓库级生成中不同类型检索信息的价值。两项工作可以从任务粒度、信息来源和方法依赖三个维度建立联系。论文应说明本研究究竟在哪个维度作出了新的设计或获得了新的证据，避免只用“与已有方法不同”结束比较。

### 段落内部也需要有可解释的推进

一个段落通常先提出本段要解决的判断，再给出事实、实验或方法说明，并解释这些内容怎样支持判断。段落之间的连接应对应真实关系：上一段发现了什么问题，下一段准备解决什么；某个假设为何成立，后续设计因此受到了什么约束。

可在起草前简要记录每段的读者问题、证据来源及其与相邻段落的关系。这种内部论证图尤其适合新写引言、重组方法章节或修复大跨度的论证断裂。对于已有论证清楚的一段局部润色，直接检查该段的事实、语义和前后衔接即可。

## 四、方法章节需要解释到什么程度

方法章节应同时回答设计理由与实现机制。读者既需要知道“为何选择这一方案”，也需要有足够信息判断该方案是否真的具备所宣称的能力。

对于算法研究，关键内容通常包括对象与变量定义、输入输出、主要计算或决策步骤、关键参数、约束与边界条件。对于软件系统研究，还需要交代模块之间的数据流、外部信息访问、状态变化，以及与研究贡献有关的实现选择。对复现结果有实质影响的随机性、资源预算、筛选和失败处理规则，也应在方法或实验设置中明确记录。

以仓库级软件修复为例，若方法使用“问题定位—补丁生成—补丁选择”的流程，读者至少需要理解：定位结果怎样约束候选编辑位置，候选补丁怎样形成，测试反馈在何处改变选择结果，最后提交的补丁满足什么选择条件。这些关系决定了方法的科学含义。源码的内部函数名和无关的工程细节则可以留在实现文档中，不必逐行搬进论文。

实际写作时，可以核查五类信息：处理的任务和数据结构是否明确定义；每个关键步骤的输入、操作及输出能否对应；关键设计回应了哪项研究困难；参数与数据可见性是否影响方法成立；实验是否检验了关键机制。这些问题提供信息完整性的检查范围，具体叙述顺序由算法和读者的理解依赖决定。

为满足篇幅要求，可以删除重复解释、次要实现细节和无信息的修辞，同时保留读者判断机制与复现条件所必需的内容。已有方法描述准确而充分时，没有必要为了篇幅数字进行重写。

## 五、实验结果怎样形成可信的文字结论

结果章节的核心任务是回答研究问题。统计数字提供证据，正文负责说明比较条件、变化幅度和实际意义。特别需要区分三层判断：观察到了什么、可能由什么机制解释、实验还不能排除哪些替代解释。

### Agentless 的补丁筛选消融示例

*[Agentless: Demystifying LLM-based Software Engineering Agents](https://arxiv.org/abs/2407.01489)* 在 SWE-bench Lite 的 300 个问题上比较补丁选择方式。论文 Table 4 报告了以下累计配置：

| 补丁选择配置 | 修复成功数 | 成功率 | 额外平均成本 |
| --- | ---: | ---: | ---: |
| 多数投票 | 77 | 25.67% | $0.00 |
| 进一步使用回归测试 | 81 | 27.00% | $0.01 |
| 再进一步使用复现测试 | 96 | 32.00% | $0.25 |

从多数投票到回归测试筛选，成功数增加 4 个，成功率提高约 **1.33 个百分点**。在已有回归测试筛选的基础上再使用复现测试，成功数增加 15 个，成功率提高 **5.00 个百分点**。从首项配置到最后一项，整体增加 19 个成功修复，差异约为 **6.33 个百分点**。

正文中可以这样组织这一结果（以下英文为依据表中数值独立撰写的说明）：

> On the 300 SWE-bench Lite instances, majority voting selected patches that resolved 77 issues (25.67%). Adding regression-test filtering increased this count to 81 (27.00%), while incorporating reproduction tests further raised it to 96 (32.00%). The final filtering step therefore contributed 15 additional resolved issues, corresponding to a 5.00-percentage-point increase under the evaluated configuration. This result supports the usefulness of reproduction-test-based selection within this pipeline, with a reported additional average cost of $0.25.

这种表述使比较对象、分母、绝对变化及百分点变化同时可见。额外成本与最终选择效果被放在同一配置下解释，读者也能识别改进所需的代价。若进一步写成“所有软件修复任务都会获益”，则已经超出这张表提供的任务范围。

仅凭三项汇总成功数，仍无法计算配对设置下的显著性检验结果，也无法判断增加的成功修复集中在哪些问题类型。要分析测试筛选到底识别了哪些错误补丁，需要逐实例候选、测试反馈和最终结果。写作时应按照现有证据的强度提出机制解释，并在必要处明确哪些判断还需要补充分析。

### Results、Discussion 与有效性威胁的职责

Results 主要报告研究问题的答案及其直接证据，包括主结果、消融、稳健性和必要的反常情况。Discussion 进一步解释多个结果之间的联系、代价、机制的可能性及实践意义。Threats to Validity 则说明哪些测量、数据和研究设计条件会影响这些解释的可靠性或推广范围。

实验设置中必须交代的关键事实，应在结果前让读者知晓。影响结果解释的异常或失败，也应在结果附近说明。系统性的局限分析可以在专门章节展开，使重要贡献与其适用范围都获得充分论证。这样的安排能够减少每个正面结果后重复相同免责声明的问题，同时保持科学判断准确。

## 六、学术表达与论文修订

### 用具体对象、动作与证据代替空泛修辞

技术写作中的许多低信息密度句子缺少研究对象或可核查内容。例如，“The proposed framework significantly improves performance” 未说明改进对象、比较基线、指标、幅度以及 `significantly` 所指的统计意义。修订应回到数据与研究问题，写清这些信息；缺少任何一项时只陈述已获支持的部分。

学术语言需要准确的主语和动词，也需要自然的逻辑衔接。`however`、`therefore` 等连接词只有在段落间存在相应关系时才有效。机械地替换连接词、列出禁用单词或者统一句长，会使文字表面规整，却无法修复推理缺口。

准确的贡献表述应直接呈现工作实际解决的问题、方法的具体作用和证据支持的结果。真实的重要限制应当说明，但不必在每段末尾重复形式化的自我削弱。使用 `novel`、`significant` 等评价词时，应核对其科学含义与证据，不能依赖语气强弱替代判断。

### 局部修改应保留已成立的论证

论文修改通常存在明确范围：调整一个定义、补足方法说明、回应一次结果解释，或重新组织整节论证。修改前应检查现有文字是否真的存在问题，再确定需要改变的事实、关系和表达。清楚、准确、与上下文一致的原文可以保持不动。

局部编辑还需要照顾相邻段落及全文共享的术语。修改某个模块名称或评价条件后，相关图注、表格标题与结果叙述可能需要同步；调整普通句式则通常无需全稿重写。结构性修改若会改变贡献定位、方法含义或结论强度，应由研究者确认科学选择。

对于 LaTeX 稿件，`\cite{}`、`\ref{}`、`\label{}`、数学环境、自定义宏和交叉引用都是文本意义与编译结构的一部分。修订应在可复制的 `.tex` 源文本上进行，必要时保留原文和修改后的完整对照，防止引用键、公式或排版命令在普通文本改写中丢失。若作者需要跨语言核对，可以同时提供准确的译文；译文用于确认语义，并不替代最终的 LaTeX 源码检查。

### 读者参与对复杂修订尤其有价值

Vercel 的 [Writing Guidelines](https://github.com/vercel-labs/writing-guidelines) 强调按读者任务组织内容、检查句子的具体信息贡献；Anthropic 的 [doc-coauthoring](https://github.com/anthropics/skills/tree/main/skills/doc-coauthoring) 将资料收集、内容组织和读者检查分开处理。这些做法对论文修改提供了实践启发：论证结构存在重大取舍时，可先呈现问题和备选结构，再依据作者判断继续；明确的局部语言任务可以直接编辑，不需要额外建立一套审批流程。

共创过程中的提问数量、候选段落数量和修改轮数由实际任务决定。学术论文还需要独立的事实来源与科研证据检查，通用写作规范无法代替领域研究者的科学判断。

## 七、从材料阅读到定稿的工作方法

一套有效的写作过程应使每次修改都能回到原始问题和证据，且不会为简单任务增加不必要的步骤。

**准备材料。** 先核对目标章节、论文类型、目标读者以及作者已确认的贡献和术语。读取必要的相邻正文、实验表格、论文引用和方法定义。缺少关键证据时，应指出实际缺口；不能根据流畅程度推测实验结果。

**安排论证。** 对新写或大幅重组的部分，先确定章节所回答的读者问题，安排段落职责和证据。必要时形成简短的内部论证图，使方法、相关工作和结果能够逐项回应前文提出的困难。对仅修改一段措辞的任务，只需核对其局部职责与上下文。

**写出技术内容。** 按读者理解需要引入概念，再说明具体机制、必要条件和关键数据。研究方法应在展开工程细节之前交代设计理由；结果应直接回答研究问题，并选择改变读者判断的证据。

**检查论证。** 核查主张与证据的对应、必要定义、实验条件、数值、技术跳跃与段落重复。遇到证据不足时，先明确科学问题的处理方式，再修订文字。

**编辑语言。** 在内容准确的基础上调整主体、动作、句子节奏和逻辑连接，删除不承担论证职责的文字，保持必要技术细节和来源条件。

**核对受影响内容。** 检查修改后章节与论文其他位置的主张、术语、数字、引用及图表是否一致。LaTeX 编辑还需要核对源文件结构；如任务涉及编译，可在目标环境中检查实际结果。检查范围由变更影响决定，不要求每次普通润色都执行全文审计。

论文的论证、语言和来源关系已经满足修改目标时，就可以停止。进一步重写应有明确的内容收益，避免仅为了增加篇幅、压缩到任意页数或制造形式上的修改记录而改变成熟文字。

## 八、主要参考资料与证据范围

- Cassano et al., *Knowledge Transfer from High-Resource to Low-Resource Programming Languages for Code LLMs*, OOPSLA 2024 / PACMPL. [DOI: 10.1145/3689735](https://doi.org/10.1145/3689735)。用于分析数据质量问题、替代方案与方法验证之间的写作关系。
- Chen et al., *Code Search Is All You Need? Improving Code Suggestions with Code Search*, ICSE 2024. [DOI: 10.1145/3597503.3639085](https://doi.org/10.1145/3597503.3639085)。用于分析从开发者任务与检索问题收窄动机的路径。
- Gu et al., *What to Retrieve for Effective Retrieval-Augmented Code Generation? An Empirical Study and Beyond*, ICSE 2026. [会议论文页面](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/182/What-to-Retrieve-for-Effective-Retrieval-Augmented-Code-Generation-An-Empirical-Stud)。用于分析初步实证观察如何决定后续方法设计。
- Chen et al., *ArkAnalyzer: The Static Analysis Framework for OpenHarmony*, ICSE 2025 SEIP. [DOI: 10.1109/ICSE-SEIP66354.2025.00018](https://doi.org/10.1109/ICSE-SEIP66354.2025.00018)。用于分析具体语言和工具差异形成工程研究动机的方式。
- Xia et al., *Agentless: Demystifying LLM-based Software Engineering Agents*, FSE 2025. [论文与 Table 4](https://arxiv.org/abs/2407.01489)。用于分析研究问题、消融数据、成本与证据强度之间的关系。
- [Vercel Writing Guidelines](https://github.com/vercel-labs/writing-guidelines) 与 [Anthropic doc-coauthoring](https://github.com/anthropics/skills/tree/main/skills/doc-coauthoring)。用于分析读者导向的文字诊断及复杂文档共创过程。

这些参考提供了可观察的写作组织方式、技术表达案例和实践建议。具体论文的研究结论应以其原始任务、数据和发表版本为准。不同研究类型可以采用不同的论证顺序；单靠模仿公开论文的文字形式，无法证明另一项研究的学术主张成立，也不能保证投稿结果。

## 九、从研究结论到 `academic-writing` Skill 的设计

前文分析可以归纳为一项实际写作要求：Agent 需要根据论文的研究问题、现有证据和当前修改范围，决定应该组织哪些论证、保留哪些技术信息，以及如何准确表达研究结论。这些判断需要落实到具体任务行为，才能在论文起草和修改时重复使用。

### 9.1 明确职责和所需材料

`academic-writing` 面向计算机科学论文的章节起草、论证重组、局部修订、学术表达和与写作直接有关的一致性检查。其入口文件 [SKILL.md](../../../skills/academic-writing/academic-writing/SKILL.md) 要求 Agent 先识别任务范围，再读取当前稿件、相邻章节、已确认的研究主张和相关证据。

这一设计来自第一、三、六节的分析：论文各段承担的论证职责由研究内容决定；现有表述可能已经足够准确；没有核实的实验事实不能靠语言生成补齐。因此，对单段润色只检查必要上下文，对新建章节或大幅重组才建立完整的论证关系。任务规模直接决定所需材料和工作深度。

### 9.2 将专业规律转化为可执行规则

| 前文的研究认识 | Agent 需要采取的具体行动 | 对应文件 |
| --- | --- | --- |
| 研究主张需要事实、实验或可解释的推理支持（第一节） | 追溯重要主张的依据；发现断裂时补充可核查证据、收窄主张或指出待确认问题 | [SKILL.md](../../../skills/academic-writing/academic-writing/SKILL.md) |
| 不同论文可以采用不同的动机与论证路径（第二、三节） | 按读者问题安排章节和段落职责；必要时参考相近论文的论证方式，不固定段落数量或照搬措辞 | [argument-and-section.md](../../../skills/academic-writing/academic-writing/references/argument-and-section.md) |
| 方法必须交代设计理由与足够的技术细节（第四节） | 核查困难与机制的对应、输入输出、状态、算法、参数、假设及必要的复现条件 | [SKILL.md](../../../skills/academic-writing/academic-writing/SKILL.md)、[argument-and-section.md](../../../skills/academic-writing/academic-writing/references/argument-and-section.md) |

这些规则把研究结论转化成 Agent 能够执行和检查的动作。每项动作都有明确的适用情境，避免把“专业、严谨、自然”等一般要求当作完整方法。

### 9.3 为什么采用一个入口和三份参考文件

[SKILL.md](../../../skills/academic-writing/academic-writing/SKILL.md) 保存所有论文写作任务都会涉及的决策：识别范围、核对材料、组织论证、修订正文、检查结果和交付。较深入的方法放在三份参考文件中，以便按照任务性质读取。

- **`argument-and-section.md`**：处理新建章节、论证结构不清、方法动机不足等问题，保存章节职责、段落关系和公开论文的可迁移经验。
- **`results-and-claims.md`**：处理 Results、Discussion 以及涉及实验数字的摘要和引言，保存比较口径、效应解释、证据强度和跨章节一致性检查方法。
- **`editing-and-latex.md`**：处理局部修订、语言编辑和 LaTeX 源码修改，保存改动范围判断、语义保护和不同交付形式的具体操作。

例如，用户只要求改进 Introduction 的研究动机时，Agent 应重点检查最近工作与方法理由的关系；若要求解释一组消融结果，则重点读取结果证据的处理方法；若要求精修一段 LaTeX，则重点核对局部语义和源码命令。按任务读取相关细节可以减少无关规则对当前写作的干扰。

### 9.4 用任务边界保护科学判断

学术写作能够改善论证的组织和表达，也能够发现明显的证据缺口。核心研究问题、贡献定位、实验协议和证据解释的实质性改变仍需要作者作出科学判断。因此，Skill 允许在既定范围内直接完成文字和局部结构修订；需要改变研究立场或关键技术含义时，应先指出具体影响。

当任务转向正式审稿意见与回复、独立论文评审或逐项核验原始实验记录时，分别由 `paper-revision-response`、`independent-paper-review` 和 `research-integrity-audit` 承担主要职责。明确这些边界，使 `academic-writing` 能够集中完成论文论证和正文写作，避免一次普通修改被扩展为全部科研活动。

由此形成的 Skill 设计与前文研究认识保持对应：以读者问题组织论证，以原始证据控制主张，以必要技术信息保证解释完整，以分层参考文件支持不同写作任务，并以最小必要修改保护已经成立的学术内容。
