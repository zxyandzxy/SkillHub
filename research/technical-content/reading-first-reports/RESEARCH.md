# 可独立阅读的技术报告：信息结构、证据组织与多格式交付

长篇技术报告的阅读方式与技术演示不同。读者可以从头到尾阅读，也可以只读其中一节、沿目录寻找某个技术问题、从搜索结果直接进入图表。即使没有作者在场解释，正文仍需提供理解所依赖的定义、条件和引用。阅读型报告的专业质量主要体现为：读者能否快速定位问题，沿清楚的论证获得答案，并从原始材料核查重要事实。

## 一、读者如何进入并理解一份长报告

一份介绍自动代码修复的报告，可能同时服务三种读者。初次接触领域的人需要先理解什么是仓库级问题修复；熟悉 SWE-bench 的研究者关心基线和评价协议；复现者可能只想寻找环境配置与运行入口。三种阅读路径应当通向同一组有事实依据的解释，但不必经过完全相同的页面顺序。

为此，标题需要表达可检索的内容，目录需要反映章节关系，重要结论需要能够通过稳定链接再次定位。标题“实验二”只能告诉读者一个序号；“补丁筛选在什么任务集合上提高了修复数量”则说明该节的阅读目标。标题、摘要、图注、参考文献不只是排版元素，它们共同构成报告的导航与事实索引。

W3C 的[页面结构教程](https://www.w3.org/WAI/tutorials/page-structure/headings/)强调以语义标题表示页面结构，使读者和辅助技术能够理解内容层次。长报告使用这种组织方式，可以让视觉目录、浏览器内查找、屏幕阅读器导航和深链接访问指向相同的信息层级。视觉上的字号差别无法替代真实标题语义。

## 二、内容结构取决于问题与证据

报告的每一节需要承担明确的解释职责：指出正在处理的技术问题，定义必要概念，展示方法或证据，说明该结论的条件。面对复杂机制，可以使用一个持续复用的具体例子，让相邻章节共享术语与状态。涉及有争议的效率主张时，先说明工作负载和测量方式，再解释性能差异；否则读者容易把单次测试结果理解为所有环境下的规律。

文本、表格和图形承载的信息不同。连续段落适合展示论证与推理；列表适合真正并列的事项；表格适合精确呈现多维比较；图形适合展示结构、趋势或关系。将每个段落都放进独立卡片，会弱化段落之间的推理联系，并给移动端阅读制造额外间距。学术报告尤其需要把数字、比较对象、数据集、指标方向与解释连在一起，而不能将这些信息分散到互不关联的视觉容器。

以 Agentless 为例，说明“修复成功率”应先明确任务集合、成功的判定方式，以及数字来自作者论文还是独立复现实验。图表中的方法名称与论文版本也应保持一致。引用研究论文时，摘要式转述只是检索入口；决定性数值需要回到论文的实验表格或原始结果。写出来源位置使报告可以被复核，也能减少不同版本互相混用的风险。

## 三、图表与交叉引用需要独立可理解

读者可能通过搜索直接看到一张性能图，而没有阅读其前面的章节。因此图注应该说明指标、单位、数据来源、比较条件及图中符号。图表周围的正文则解释这些数值对研究问题意味着什么。两个部分分工明确：图注负责让图能被正确阅读，正文负责推导科学判断。

连续页面经常跨不同设备排版。“如右图所示”“见上一页的图”依赖固定空间位置，响应式重排后会失效。使用图号或语义链接可以让引用保持稳定。关键表图、方法段落和代码示例建立锚点之后，报告便能支持引用者直接链接到证据，而不是只分享整篇文档地址。

长代码块、数学公式和多列表格还需要保留阅读顺序。对于无法在窄屏完全展开的表格，允许局部横向滚动，但行名、列名和指标单位不能丢失。对于能转换为小图的数值，也不能因视觉简洁而删除改变比较结论的基线或置信区间。

## 四、技术实现应服从文档职责

静态 HTML 和 Markdown 已经可以支撑大量技术报告。需要交叉引用、可重复生成的公式和 PDF/HTML 多格式交付时，[Quarto](https://quarto.org/docs/output-formats/html-basics) 提供文档导航、引用与输出管理。需要长期维护的数据绑定界面时，[Observable Framework](https://observablehq.com/framework/) 可以把图形与数据源组织成站点，但其工程代价不适合仅有少量静态图表的文章。

选择工具时，应首先确认报告是否需要运行环境、是否必须离线、是否需要作者进一步编辑，以及是否需要读者交互。大型前端工程、动画系统或固定视口不是报告质量的必要条件。越多脚本控制核心内容，就越需要考虑脚本加载失败、搜索爬取、离线访问、键盘操作和打印版本之间的一致性。

渐进增强能够降低此类风险：先让语义 HTML 包含正文、证据与链接，再增加筛选、目录状态或可选图形交互。JavaScript 不可用时，读者可以失去某种探索便利，却不应该失去理解主要结论所必需的材料。这一原则也避免把普通折叠和导航误当成必须使用交互式教程的理由。

## 五、响应布局、可访问性和 PDF 是同一内容的不同出口

桌面阅读通常允许较宽的侧边目录；手机浏览则需要正文和图表重新排布。应保持字号、行宽、标题间距和触摸目标可读，不把固定的桌面页面等比缩小。动态控制需要可识别标签、键盘焦点和可操作状态。对于具有运动效果的图表，应尊重用户的减少动态效果偏好，并使用文字或静态状态保留解释。

[WCAG 2.2](https://www.w3.org/TR/WCAG22/)提供可供检查的键盘访问、内容重排、焦点和非文本信息准则。它可以帮助找到明确的可访问性缺陷，但并不替代报告中专业事实的审核。界面满足键盘要求，仍可能存在错误引用或误导性图表。

打印版本尤其能暴露网页文档结构的问题：标题孤立在页尾、表格被截成两半、长公式溢出、正文中指向悬停说明的解释丢失、折叠内容没有展开。实际生成 PDF 并逐页核对，是独立的交付检查。仅编写打印样式或保证页面在浏览器正常显示，不足以证明打印产物正确。PDF 可能省略可选的数据筛选，但应保留图表的核心比较和静态结论。

## 六、从研究方法到阅读型报告 Skill

以上方法形成一条清楚的工作关系：先判断读者要解决的问题和可用证据，再设计可多入口阅读的章节与交叉引用，最后依据交付场景选择技术实现并验证真实输出。[reading-first-reports Skill](../../../skills/technical-content/reading-first-reports/SKILL.md) 以此为主线安排任务。

| 研究结论 | 对 Agent 的具体要求 | 规则位置 |
| --- | --- | --- |
| 报告需要支持不同进入路径（第一节） | 识别读者问题，建立摘要、语义标题、目录及稳定深链接 | [information-architecture.md](../../../skills/technical-content/reading-first-reports/references/information-architecture.md) |
| 图表与正文需要形成可复核的证据关系（第二、三节） | 统一编号、定义、实验条件与引用，检查跨章节事实是否一致 | [information-architecture.md](../../../skills/technical-content/reading-first-reports/references/information-architecture.md) |
| 交付工具取决于实际文档需求（第四节） | 优先现有 HTML/Markdown，需要多格式或数据绑定时再引入框架 | [SKILL.md](../../../skills/technical-content/reading-first-reports/SKILL.md) |
| 主要结论不能依赖脚本或悬停（第四、五节） | 保留语义正文与静态出口，并检查键盘和脚本失败路径 | [responsive-and-print.md](../../../skills/technical-content/reading-first-reports/references/responsive-and-print.md) |
| 网页与 PDF 的阅读证据需要分别检查（第五节） | 实际导出并核对分页、图注、代码和引用，记录未检查的出口 | [responsive-and-print.md](../../../skills/technical-content/reading-first-reports/references/responsive-and-print.md) |

Skill 的核心指令负责路由、任务输入、内容优先顺序和完成边界；两份按需参考资料分别处理信息结构与交付验证。固定页面的技术讲解由 `technical-presentations` 承担；通过操作变量揭示机制的教学任务由 `interactive-explainers` 承担。这样可避免仅因技术报告含有少量目录或交互元素就引入不必要的复杂实现。
