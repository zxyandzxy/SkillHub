# 面向理解的技术写作：知识依赖、实例和证据保持

技术文字通常面对一个已经具备部分专业知识的读者。读者不一定需要从头学习整个领域，却需要在有限篇幅内理解某个问题、机制和实际影响。文章能否完成这一任务，取决于作者是否准确判断读者缺少哪些先备知识、按照什么顺序建立概念，以及能否把抽象结论连接到具体例子。

技术文章、教程、领域综述和论文改写的主要阅读任务不同。概念解释帮助读者形成正确的心智模型；教程让读者在给定环境中完成可复现操作；领域综述帮助读者比较方法和选择技术；论文面向工程读者的改写则要把科研证据转换成更容易理解的叙述。共同要求是技术事实可查、语义连续、关键条件不丢失。

## 一、解释中的知识依赖

### 决定读者先要知道什么

解释复杂技术时，作者很容易沿用原始资料的术语顺序。例如，一篇关于自动软件修复的论文可能直接使用 repository-level context、patch selection、regression test 和 reproduction test。如果读者尚不理解“补丁是什么”和“测试究竟在判断什么”，即使逐句翻译这些术语，也无法理解它们在系统中承担的作用。

更可靠的安排是从最终需要解释的问题反推先备知识。解释补丁筛选时，可以先给出一个出现错误的代码仓库与待解决的 Issue，再说明修改代码会形成候选补丁；不同补丁需要依靠既有测试检查是否破坏功能，也可以用针对原始问题构建的复现测试判断错误是否已解决。读者理解这些对象后，才能判断为什么补丁生成与最终补丁选择属于不同环节。

先备知识不需要无限展开。读者已经理解 Git 的分支和提交，就无需为了说明补丁重新介绍版本控制发展史。每项背景都应能回答“若不解释它，读者会在哪个后续步骤产生误解”。背景深度取决于任务与读者表现，不应简单按照学历或岗位作固定分组。

### 术语、符号和例子的连续性

一旦开始使用某个例子，文章应尽量保持相同的对象和变量。介绍线性 Attention 时，若先用一个 token 的 query、key、value 说明计算关系，后续进入矩阵运算应解释向量如何在多个 token 上扩展；不要在不同段落中突然改变符号方向和矩阵含义。算法讲解中的图形颜色、箭头和变量名也承担相同的识别职责。

技术解释中常见的另一种问题是混淆真实系统与教学简化。两步的玩具程序可以展示补丁如何生成，却不能用来证明修复系统在大型仓库中有效。适当的写法应直接标明“以下示例用于解释流程”，需要评价性能时再引用真实数据与协议。

## 二、通过公开作品观察解释方法

### The Illustrated Transformer 的分层表达

Jay Alammar 的 [The Illustrated Transformer](https://jalammar.github.io/illustrated-transformer/) 借助图解逐步引入词向量、位置编码、Attention 和 Encoder–Decoder 等概念。其可迁移价值在于说明依赖次序：读者先看到输入如何转成可处理的表示，再理解 Attention 需要哪些信息，最后将局部机制放回整体结构。图形与正文相互配合，而不是把论文原图缩小后贴入网页。

对于一个需要解释注意力计算的技术作者，应该学习这种“先使对象可辨认，再解释其运算和关系”的原则。不能复制博客的原图、独特表达或默认其面向入门者的讲解篇幅适合所有受众。对于熟悉 Attention 的研究者，可以直接讨论特定数据流和性能瓶颈。

### Distill 使用反例校正直觉

Wattenberg、Viégas 和 Johnson 的 [How to Use t-SNE Effectively](https://distill.pub/2016/misread-tsne/) 通过改变参数、初始化和数据分布，说明二维可视化中的簇间距离、簇大小和形态可能被误读。该作品提供了重要的解释方法：当某种工具输出容易让读者产生过强推断时，设置一个能显示误区的反例，比追加一段“注意局限性”更有效。

这种处理方式适用于性能图、模型预测解释和软件系统示例。例如把两个修复方法在不同测试集上的通过率放在一起，读者可能直接推断谁更强。文章需要交代基准、样本与测试口径的差异，必要时用一张对照表展示比较为何不成立。

### 技术综述从比较问题组织材料

[Lilian Weng 的技术综述](https://lilianweng.github.io/) 常围绕一个研究问题展开不同技术路径，在重要机制之间建立联系。这类材料适合观察如何安排相互依赖的概念与代表方法。综述不应写成“论文 A 做了什么、论文 B 做了什么”的罗列；分类维度必须为读者的比较或决策服务。

例如比较检索增强代码生成，可以按检索的信息来源、触发时机、是否调用执行环境、生成任务粒度和评价设置组织。即使两篇文章都包含“检索”，若一个研究函数补全、另一个研究仓库级修复，直接排列成功率也不能形成公平比较。

## 三、不同文本形态如何确定结构

概念解释的主线是“要理解什么 → 用什么对象表示 → 机制怎样运行 → 何时适用及如何误解”。教程的主线则由可观察操作决定：先交代前提与环境，再给可运行步骤、每步应出现的结果、常见故障及恢复方法。教程里的命令和输出是事实性信息；未实际运行时必须说明，不应把假想终端结果写成已验证记录。

技术博客通常允许比投稿论文更早引入具体场景，也可以用不同的顺序解释动机、方法与实验。但从论文改写时必须保留最重要的证据条件。例如 Agentless 在 FSE 2025 的论文中，系统的主要评价是 SWE-bench Lite 的仓库修复任务。博客可以先讲读者关心的真实 Issue，再解释“定位—修复—补丁选择”，但不能将该论文的特定测评结果推广为所有开发任务的可靠性结论。论文中的成功率、测试集版本和比较配置不能因为面向普及读者而省略到改变含义。

局部编辑同样需要目标判断。若用户只要求把一段描述改得更清楚，作者应找出阻碍理解的地方：是缺少主语、变量定义不完整，还是事实关系本身不成立。只改变有问题的句子和必要衔接，避免在已经准确的区域反复改写。

## 四、语言准确性与事实保真

自然语言的精简应减少读者的推断负担。诸如“值得注意的是”“这一技术具有重要意义”之类句子，若没有说明具体主体、作用或证据，可以删除。若一段技术论证本身缺少中间步骤，删除连接词并不能让它变清楚，必须补足推导。

从学术论文转向教程时，常见的事实漂移有三类。第一类是范围漂移：把某个数据集、模型或设备下的结果写成一般事实。第二类是因果漂移：把观察到的性能差异解释为某个模块的独立作用，尽管没有相应消融。第三类是单位或比较漂移：忽略分母、混淆百分比与百分点，或把不同硬件配置下的运行时间混为同类数值。

这些问题需要直接回到原始证据核查。写作时可以为核心主张保留简短的来源映射：原文位置、原始条件、本次改写段落与允许变化的表达部分。它不必作为读者可见的附加表格，但可以防止改写中改变科学事实。

完整的技术解释应允许合理的简化，同时告知读者简化何时失效。举例说明一个网络协议可以省略无关封装字段，却不能把需要握手的状态转换改写成没有握手。内容准确后，再编辑句子长度、图文位置和阅读节奏才有意义。

## 五、研究方法的适用边界与参考

这些经验适合有明确读者、来源材料与技术问题的文章。没有原始论文或代码时，可说明当前内容是概念性解释，并标明具体事实需要验证。原作品提供的是写作组织的范例，不能替代当前任务的实验、代码和引用。

主要参考：[The Illustrated Transformer](https://jalammar.github.io/illustrated-transformer/)；[How to Use t-SNE Effectively](https://distill.pub/2016/misread-tsne/)；[Lilian Weng 的技术文章](https://lilianweng.github.io/)；[Agentless, FSE 2025](https://lingming.cs.illinois.edu/publications/fse2025.pdf)；[Vercel Writing Guidelines](https://github.com/vercel-labs/writing-guidelines)。案例属于各自作者的作品；这里提炼阅读顺序、机制解释与证据控制方法，不复制图文素材。

## 六、研究结论如何形成 `technical-writing` Skill

技术写作的专业增量集中在三个可操作判断：需要给读者补充哪些知识、怎样选择能反映真实机制的实例，以及改写后如何保持来源证据。于是 [SKILL.md](../../../skills/technical-content/technical-writing/SKILL.md) 首先辨别概念解释、教程、综述、论文转博客和局部编辑，再让任务性质决定后续步骤。

| 研究认识 | 落地动作 | Skill 文件 |
| --- | --- | --- |
| 解释效果取决于先备知识的顺序（第一节） | 按目标问题反推必要定义，选择稳定实例并说明其抽象过程 | [explanation-and-sequence.md](../../../skills/technical-content/technical-writing/references/explanation-and-sequence.md) |
| 公开优秀作品依靠知识顺序和反例减少误解（第二节） | 必要时分析同类公开作品的组织手法；对容易误读的工具增加具体边界案例 | [explanation-and-sequence.md](../../../skills/technical-content/technical-writing/references/explanation-and-sequence.md) |
| 不同文本用途决定不同叙事（第三节） | 概念解释、可复现教程、领域比较和跨媒介改写分别处理 | [SKILL.md](../../../skills/technical-content/technical-writing/SKILL.md) |
| 改写中容易丢失实验范围和因果条件（第四节） | 核查原始主张、数字、指标、条件和改写位置的对应 | [editorial-and-evidence.md](../../../skills/technical-content/technical-writing/references/editorial-and-evidence.md) |
| 局部修订应修复真实问题（第三、四节） | 先确认哪里造成误解，再限制编辑范围并交付实际正文 | [SKILL.md](../../../skills/technical-content/technical-writing/SKILL.md) |

采用一个主入口和两份按需参考：新建解释时重点读取概念组织方法，源材料改写时重点读取事实保持与编辑诊断。论文投稿正文由 `academic-writing` 承担，学术证据的系统检索由 `literature-research` 承担。这样的分工使技术文章能够按读者需要重组事实，同时保留可核查的技术含义。
