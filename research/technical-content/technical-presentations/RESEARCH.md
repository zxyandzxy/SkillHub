# 科研论文讲解与技术演示的内容组织方法

科研演示的第一项任务是让观众理解技术关系：研究针对的真实问题是什么，已有方法解决了哪些部分，新的机制如何工作，实验在什么条件下支持哪些结论。页面数量、配色和导出格式都应在这些问题清楚之后确定。技术演示尤其容易受到呈现媒介的影响：同一篇论文的内容，现场讲演和供读者独立阅读的版本需要不同的信息密度。

一份可以独立阅读的逐页文稿，已经能够让研究者核对学术事实和内容顺序。真正需要 PPTX、HTML 或 PDF 时，才需要解决渲染、页面布局和交互技术。这种次序使内容讨论不会被工具能力、模板风格或无法验证的视觉草图提前限制。

## 一、从研究问题建立知识依赖链

### 论文的目录不等于讲解顺序

论文正文按照科研写作的论证组织，演示则面向当前听众的知识缺口。例如对一个尚不熟悉仓库级自动修复的观众，直接展示 Agentless 的系统框图，即使图中标有 localization、repair 和 patch validation，也难以解释为何要区分这些步骤。讲解应该先定义问题实例：给定 GitHub Issue、仓库的基线提交和要通过的测试，系统需要产生能够修复 Issue 的补丁。观众理解这一任务后，才有理由讨论自动 Agent 的工具交互与非自主流程的差别。

[SWE-bench（ICLR 2024）](https://proceedings.iclr.cc/paper_files/paper/2024/file/edac78c3e300629acfe6cbe9ca88fb84-Paper-Conference.pdf)提供仓库修复的评价任务；[SWE-agent（NeurIPS 2024）](https://arxiv.org/abs/2405.15793)探讨帮助语言模型与计算机环境交互的接口；[Agentless（FSE 2025）](https://lingming.cs.illinois.edu/publications/fse2025.pdf)展示定位、修复和补丁选择的固定阶段流程。三项工作承担不同背景职责。讲解 Agentless 时，读者要理解“为什么任务需要访问代码库”“自主调用工具面临什么决策问题”“固定流程怎样组织候选补丁”，才有能力理解作者的主张。

讲解顺序因此可以按`任务 → 必要前作 → 实际困难 → 机制 → 结果及条件`调整。原论文引用数量并不决定背景页面数。某篇前作若只提供常用公式，可以在一页中简要说明；若其方法正是被改进对象，则应交代足够细节，使新旧机制的比较成立。

### 用稳定实例和符号解释多步机制

方法依赖多个动作时，保持主体和信息形状一致有助读者建立连续的心智模型。例如从仓库问题开始，后续各页持续使用相同 Issue、代码片段、候选 patch 和测试结果，仅突出本页新增的定位结果或筛选依据。若变量或颜色变化意味着操作语义变化，应在页面中解释；如果只是重新美化，布局变动会增加额外的认知成本。

Bang Wong 在 [The overview figure](https://doi.org/10.1038/nmeth0511-365) 中讨论科学流程图如何通过状态及操作连接研究过程；[Gestalt principles](https://doi.org/10.1038/nmeth1110-863)讨论相似性、接近和连接对视觉分组的影响。应用这些方法时，应让空间关系与科学关系一致。例如同一组实验条件使用一致标记，数据与控制流不能仅为视觉对称而交换箭头。

## 二、论文讲解与研究进展汇报的不同内容责任

论文讲解面向一个公开发表研究，重点是让观众重建作者的研究动机、方法和证据链。研究进展汇报的内容来源则是研究者自己的实际工作：本阶段解决了什么问题、什么仍未验证、与此前相比获得了什么新发现、哪些工作阻塞了下一步。进展汇报不能因为采用学术报告格式，就将计划中的实验写成已完成，或把实验脚本运行成功写成研究结果已经证明。

对于研究进展，一种有用的页面安排是先定位当前目标，然后报告本阶段的可核查产物，再展示少量会改变项目判断的数据和异常，最后说明仍待解决的关键问题及下一步。每页需要让观众理解一个实际变化。对于论文讲解，方法解释与动机链可能占更多页面；对于进展汇报，新的实验条件、差异和失败记录往往比完整背景更重要。

这两种任务都不应把“本轮做了什么”作为空泛标题。研究进展页应该回答具体问题，例如“候选补丁选择在新增复现测试后增加了多少成功实例”，并提供原始数据与配置。尚无数据时则直接说明待验证的机制，不用虚构趋势图。

## 三、逐页内容如何做到独立可读

### 标题、正文和图表的分工

标题最有价值的作用是使读者知道本页要回答的问题或可支持的结论。与其写“研究背景”，不如写“仓库级修复为何需要同时理解 Issue 和测试”；与其写“方法优势”，不如在有数据时直接写出真实结果及条件。正文负责解释因果、技术步骤和必要限制，图表负责提供可辨认的结构或证据。

[Garner 与 Alley（2013）](https://pure.psu.edu/en/publications/how-the-design-of-presentation-slides-affects-audience-comprehen/)在特定工程学生样本的演示实验中研究了 assertion–evidence 型页面与理解表现的关系。该研究支持认真考虑结论式标题及图文关系，但实验结论不意味着所有研究汇报都必须采用固定“一句主张＋一张图”的版式。独立阅读型演示需要保留读者无法从图中自行推断的定义、条件和必要解释。

[Nature Synthesis 的 Figuring it out](https://doi.org/10.1038/s44160-022-00067-8)强调科学图形的阅读顺序、分组与图注，使图形可以离开正文被理解。搬到幻灯片上时，必须结合页面尺寸决定图和正文如何邻接。大面积留白既不能替代技术解释，也不必然使页面更清楚；有效信息密度应与页面的阅读任务相称。

### 为什么先写逐页文稿

对复杂论文，若研究者尚未确认要向听众解释哪条因果链，直接制作整套页面可能导致大量反复返工。更有效的方法是先给每页一段可直接复制的技术文本：标题、解释、必要例子或公式、拟引用的原论文图表和出处。用户可以在阅读内容时明确指出知识缺口、顺序不合理或科学主张错误。内容已确定后再制作页面，修改成本和语义漂移风险都会降低。

[Anthropic 的 doc-coauthoring](https://github.com/anthropics/skills/tree/main/skills/doc-coauthoring)提供文档共创与读者检查的实践思路；其中固定询问数量和长篇审批流程并不适合所有演示任务。用户已准备好讲稿或只要求改一页时，应跳过重复的共创步骤。

## 四、具体图形与视觉语言怎样服务研究

关键方法图优先采用原论文可读的版本，保留真实图号、来源和含义。如果论文图极密、在目标版面缩放后无法阅读，可以先放大相关区域、增加局部标注或从权威源重绘。裁切时不能丢掉改变解释的轴、图例、实验条件或对照基线；重绘真实图表须核查原始数据和论文对比条件。由生成式图像凭记忆生成的实验曲线不具备可靠证据来源。

[FlashAttention-2（ICLR 2024）](https://proceedings.iclr.cc/paper_files/paper/2024/file/98ed250b203d1ac6b24bbcf263e3d4a7-Paper-Conference.pdf)的 Figure 3 利用可对应的布局说明两版方法的 warp 工作分配变化。技术讲解可以逐页保留同一 Q/K/V 表示，并逐步指出不同分配如何影响通信和并行；必须避免将方法图中的设计意图写成没有经过测量的性能证明。

视觉系统应优先利用对齐、分组、符号一致性和真实图文关系。Bang Wong 的 [Simplify to clarify](https://doi.org/10.1038/nmeth.1660)强调减少与解释无关的元素，这适用于无意义的卡片、装饰性箭头和重复导航文案。简化不意味着强制删掉图中必要注释，也不意味着技术页只能放很少的文字。

## 五、媒介制作及真实页面检查

PPTX 适合延续既有演示模板和人工后期编辑；HTML 适合需要浏览器导航或复杂交互的页面；PDF 适合静态分发。无论选哪种媒介，都需要在实际页面中核对结果。仅交付可复制的逐页文稿也是合理的完成状态，不要求每次生成所有格式。

真实渲染检查能发现文字超出边界、公式或图例缩得过小、字体替换、元素遮挡和导出裁切。HTML 还需要检查键盘导航、焦点、离线资源与小视口行为；静态 PDF 需要确认动画中的关键步骤不会只留下首帧。结构校验脚本能证明部分源文件关系存在，但不能证明听众已经理解复杂机制。

[Frontend Slides](https://github.com/zarazhangrui/frontend-slides)区分讲演型和阅读型信息密度，也重视浏览器的最终效果。[Anthropic pptx Skill](https://github.com/anthropics/skills/tree/main/skills/pptx)讨论编辑既有文件与实际渲染验证。这些方法可以借鉴，但不能把固定主题、字数和投影尺寸视为通用要求。

需要分享第三方论文插图、图标、字体和主题模板时，应先确认版权与再分发范围；公开可阅读不代表能复制入公开仓库。演示内容中的实验数据也应保留原始语义及作者的来源说明。

## 六、研究结论如何形成 `technical-presentations` Skill

研究内容可以落实为三个层次的行动：先识别研究事实与听众知识缺口，再组织可独立阅读的逐页内容，最后在用户需要时制作文件并检查实际呈现。[SKILL.md](../../../skills/technical-content/technical-presentations/SKILL.md) 按此顺序规定工作范围，防止工具选择越过内容理解。

| 研究认识 | Agent 的实际动作 | 对应 Skill 文件 |
| --- | --- | --- |
| 论文讲解要补足关键前作与技术动机（第一节） | 追踪少数必要相关工作，构建问题、机制、证据的知识链 | [research-story.md](../../../skills/technical-content/technical-presentations/references/research-story.md) |
| 进展汇报依赖研究者真实状态（第二节） | 区分已完成、待验证与异常，不以既定页数凑内容 | [research-story.md](../../../skills/technical-content/technical-presentations/references/research-story.md) |
| 页面需独立回答读者问题（第三节） | 先输出可复制逐页稿，标题、正文、图表和来源互相对应 | [slide-content.md](../../../skills/technical-content/technical-presentations/references/slide-content.md) |
| 图形结构应遵守科学语义（第四节） | 复用合法的原论文图；多步机制保持图形稳定，修改时核对原始数据 | [slide-content.md](../../../skills/technical-content/technical-presentations/references/slide-content.md) |
| 媒介选择由交付需要决定（第五节） | 仅在要求制作文件时选择 PPTX/HTML/PDF，展示真实渲染并核查导出 | [render-and-deliver.md](../../../skills/technical-content/technical-presentations/references/render-and-deliver.md) |

`SKILL.md` 是任务入口，保存内容形成顺序与最重要的科学边界；三份参考文件分别负责研究知识链、逐页内容和实现检查。技术文章的长篇解释由 `technical-writing` 承担，论文投稿正文由 `academic-writing` 承担，独立研究图表则由 `research-figures-tables` 承担。技术演示的主要职责是将已核实的研究组织为听众能够沿页面理解的叙事。
