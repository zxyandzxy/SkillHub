# 用户界面的质量：任务流程、视觉层级与可验证交互

一张漂亮的界面截图可以展示颜色、间距和布局，却很难说明用户是否能完成真正的任务。用户可能找不到主要操作、提交失败后丢失输入、无法通过键盘访问弹窗，或在窄屏下看不到表格的关键字段。UI/UX 工作需要同时组织信息、操作、反馈和视觉表达，并在真实运行状态中验证，而不能只依据单个静态画面判断完成。

设计时还需要区分证据的层次。设计规范和启发式原则有助于发现常见缺陷，真实用户研究才能观察目标用户是否理解流程，而实际功能测试则确认实现是否按预期工作。它们提供不同证据，不能相互代替。

## 一、以用户任务决定信息和交互顺序

界面设计首先要明确用户是谁、怎样进入当前功能、需要完成什么、哪些信息决定下一步操作，以及成功或失败后应看到什么。若一个设置页的主要任务是修改账户偏好，那么当前值、保存方式、失败反馈和退出后的持久状态，比把所有选项包装成漂亮卡片更加重要。

[Jakob Nielsen 的十项可用性启发式原则](https://www.nngroup.com/articles/ten-usability-heuristics/)包括系统状态可见、界面语言贴近用户、保持一致以及帮助用户识别与恢复错误等。这些原则不是每个产品都必须采用的固定布局，而是用于检查具体交互问题的判断工具。某个页面的按钮位置是否合适，仍取决于用户任务、平台习惯与可观察结果。

在设计复杂流程时，先安排用户需要知道什么、做出什么决定、操作后获得何种反馈，再决定使用弹窗、步骤条、标签页还是侧栏。组件选择不能反过来决定业务规则。例如需要用户在提交前确认不可逆删除，就应依据操作风险设计确认或撤销，而不是因为视觉模板里没有对话框就省略必要保护。

## 二、视觉系统是帮助阅读和行动的约定

排版、留白、对齐、颜色和组件状态帮助读者快速识别层级与操作优先级。标题应说明真实内容，主要操作需要可发现，次要信息可以在需要时展开。颜色表达语义时应稳定，例如警告、成功和错误的用法不能在不同页面任意改变。

一个已有产品通常已经有字体、间距、组件和交互约定。新页面应优先复用这些规则，以降低学习成本和维护复杂度。没有设计系统时，建立少量语义化的背景、正文、按钮、错误和状态 token 通常比每个组件独立设定样式更可靠；但不需要为了一个小页面建立庞大的设计基础设施。

视觉一致性也不能脱离实际内容。超长标题、密集表格、动态数字和真实错误信息会改变布局，因此不能只用几条占位短文评价设计。审美上的整齐有时掩盖了被裁切的字段或难以理解的按钮；应以实际阅读任务检查布局是否真的提高了理解效率。

## 三、真实界面具有默认状态以外的大量行为

用户可能打开空列表、网络请求正在加载、表单有非法输入、权限不足、服务返回错误，或在提交过程中切换页面。如果设计只覆盖理想成功路径，实际使用就容易出现空白、重复提交、无法恢复的错误或丢失用户输入。

状态设计需要按功能覆盖适用场景，而不是机械给每个按钮生成所有状态。一个文件上传组件至少可能涉及待选择、上传中、完成、失败、取消以及文件格式错误；普通静态说明文字没有必要人为增加禁用与加载状态。需要核查的是当前用户行为下真正存在的状态及其反馈。

错误文案也是设计组成部分。“请求失败”只能告诉用户发生异常，“保存未完成，请检查网络后重试；输入内容仍已保留”才能帮助恢复操作。但这类文字必须反映系统真实保证，不能在数据可能已经丢失时声称内容已保存。

[GOV.UK Design System](https://design-system.service.gov.uk/)提供面向真实公共服务任务的组件、表单和错误提示实践，值得借鉴清楚的用户语言与一致行为；不能把其视觉规范视为所有行业的统一风格。

## 四、无障碍要求约束实际交互方式

键盘、触摸、放大文字、屏幕阅读器和不同屏幕尺寸都会改变使用路径。Web 页面应使用具有正确语义的输入与按钮，提供可见焦点、合理的阅读顺序和足够的触摸目标。重要状态不能只以红色或绿色区分，也不应把完整操作隐藏在只能鼠标悬停才能出现的位置。

[WCAG 2.2](https://www.w3.org/TR/WCAG22/)为内容可操作性、可辨识性、焦点和响应重排等方面提供可核查准则。平台也有各自约定，例如 [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/)与 [Microsoft Fluent](https://fluent2.microsoft.design/) 分别反映对应生态的交互习惯。无障碍检查应依据真实目标平台选择，不机械把所有网站规则套给原生桌面应用。

可访问性并非最后添加的装饰性验收。信息顺序、操作标签和状态反馈在最初设计时就会决定一些用户能否完成任务。将这些问题推迟到发布前才处理，往往需要重新修改界面结构和交互逻辑。

## 五、实际渲染与用户研究形成不同证据

真实页面检查能发现静态图看不到的错误，例如操作之后焦点丢失、表单反馈位置变化、窄屏布局溢出、错误状态无法返回和弹窗遮挡。应在目标应用中使用代表设备与内容操作主要任务，记录观察到的问题和具体修改，再检查受影响状态。

静态截图只能证明某个页面在某一窗口和时刻的外观。启发式评审根据设计原则给出可能问题；自动化交互测试检验规定路径和结果；可用性测试则需要真实或代表性用户完成目标。若没有用户研究，最多说明依据何种原则和实际操作改进了设计，不能宣称用户满意或真实用户效率已经得到实证提高。

体验工作还要注意交付边界。用户只要求修复一处按钮布局时，沿用现有视觉规则完成局部修改即可。涉及新的任务流程、重要数据要求或权限变更时，应把这些决定交由相应需求与系统设计工作确认，避免界面修改偷偷改变产品行为。
