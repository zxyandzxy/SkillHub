# 软件代码评审：需求符合度、真实变更与可复核发现

代码评审常被缩小为查找命名问题或不够优雅的实现。然而功能可能通过编译、单元测试和风格检查，仍然没有解决用户真正提出的问题；也可能实现了功能，却破坏数据一致性、权限边界或接口兼容。成熟评审需要同时回答两个问题：实现是否符合原始要求，以及实现是否带来了可复核的工程风险。

评审的价值取决于证据质量。指出一个可定位、能够在特定条件触发的严重问题，比列出几十条主观风格意见更有帮助；完全没有发现问题，也只代表已经检查的范围，不能据此宣布系统在所有场景中正确。

## 一、先确定正在评审的实际对象

评审可能针对 PR、两个指定提交、单个补丁、尚未提交的工作区，或没有版本控制的源码。不同对象需要不同的差异基准。若比较分支变更，应根据共同祖先确定新分支引入了哪些提交；若评审当前工作区，则需要同时考虑暂存、未暂存和未跟踪的新文件。仅运行 `git diff HEAD` 不能涵盖用户尚未 `git add` 的新文件，也不能自动代表远程 PR 的精确差异。

变更范围确定后，还要读取需求、项目约定、主要调用方以及受影响测试。对于“修复播放器暂停后恢复位置错误”，评审目标应至少包含用户可见的播放状态和场景，而不能只看某个函数是否写得简洁。如果没有原始需求依据，就明确说明需求符合度无法完整评估，同时可以继续检查真实代码中的明确错误。

评审应维持只读边界。查证需要运行测试或打开实际应用时，先确认现有权限和环境成本；收到“评审这个 PR”不意味着自动获得修改分支、回复讨论或合并的授权。

## 二、需求符合度与工程质量需要分别检查

### 需求符合度：是否解决正确问题

从原始任务提取重要行为、验收条件和未要求的副作用。对应代码与验证证据判断功能是否实现、重要边界是否遗漏、是否引入额外行为，以及跨模块改动是否影响其他用户路径。

例如用户要求给导出功能添加日期过滤，修改后虽然生成了文件，但查询把结束日期当成不包含当天，导致最后一天数据丢失。若只读代码风格或检查下载按钮是否工作，很难发现真正的需求违背。审查者需要从“过滤规则是什么”构造独立预期，并定位到实际比较表达式。

这种评审不是直接替代测试。它可以指出测试是否独立验证需求、是否只断言返回非空、是否错误地从实现生成 expected；若缺少关键场景，按需要提出具体测试，而不是凭测试数量作判断。

### 工程质量：改变是否安全且可维护

沿真实调用链检查状态、资源、外部输入、失败路径与依赖。数据库写入可能涉及事务原子性；网络重试可能造成重复副作用；鉴权变化需要检查可信服务端边界，而不仅是前端按钮。性能敏感路径需要可比较的测量，不因为看到一段新缓存逻辑便推断更快。

工程问题应该能说明可观察的后果或可靠的风险机制。例如“某重试请求没有幂等键，外部支付成功但本地超时后会再次扣费”具有明确触发链；“最好提炼一个帮助函数”若没有具体耦合或理解风险，通常只是风格建议。

Google 的 [Code Review 指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)强调设计、功能、复杂性、测试等多维检查。可以借鉴这种证据导向的范围，而无需对每次小补丁强制所有专项审查。对安全、隐私、并发、性能和 UI 的深入核验应由实际 Diff 的风险触发。

## 三、把发现写成可以复核的工作项

有效发现应包含位置、触发条件、错误结果或未满足的要求、支持证据、实际影响和最小修复方向。例如“在 `createOrder` 的失败分支中，数据库提交已成功而响应超时；客户端重试时重复执行新增操作，没有去重检查”，给出了能继续调查的具体路径。若只是从静态代码推断可能发生，应明确其尚未通过运行复现。

评审输出应优先安排造成错误结果、数据损坏、越权或阻塞交付的问题。多个位置体现同一根因时可以合并为一个发现，说明受影响位置，而不是用条目数量展示勤奋。简单而明确的评审可以很短；对复杂系统，更多篇幅应花在解释真实故障链和证据缺口上。

对没有确认问题的评审，应写明被检查的实际范围和未执行的验证。只读检查无发现不等于编译、集成测试、生产操作已经通过。使用独立 Agent 复核可以减少单一视角依赖，但同类模型也可能沿用相同假设或产生误报，不能把“独立”当作证据本身。

## 四、收到评审反馈时如何判断

代码审查既包括给出反馈，也包括处理他人的反馈。接受建议前应核对它是否适用于当前代码、需求和兼容约束。一个审稿人建议“加通用重试以提高稳定性”，若目标操作具有不可逆副作用且没有去重措施，直接照办可能制造错误。

收到意见后可以区分四种处理：事实和风险得到确认时接受；材料不足时进一步调查；意见与现有证据冲突时给出可定位依据；涉及未确认的产品取舍时请求负责人的决定。审查者地位、意见语气和 Agent 的置信措辞都不能代替技术核实。[Superpowers 的 Receiving Code Review](https://github.com/obra/superpowers/blob/main/skills/receiving-code-review/SKILL.md)体现了先技术验证、再决定实施的实践。修复后的相关行为需要重新验证，但不自动意味着必须重复整个项目所有检查。

评论中若出现与任务无关的重构建议，应判断它是否确实降低当前风险；对已有质量的代码不必为了“展示有改进”作无理由修改。评审帮助决定下一步，而不自动获得实施和合并授权。

## 五、评审的边界与其他专业工作

`code-review-guide` 可以在审查中发现测试预期不独立、设计接口不清或项目维护问题，但主任务仍是对指定代码和需求给出事实判断。需要修复时转入编码任务；需要更完整的测试体系时转入测试任务；需要长期架构治理时转入设计和维护任务。

如果评审仅涉及一个局部变更，不需要无差别调用性能、安全、UI 和可靠性所有流程。应以可观察风险决定哪些专业信息有助于解释当前 Diff。

主要参考资料包括 [Google Code Review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)、[Superpowers 代码评审反馈处理](https://github.com/obra/superpowers/blob/main/skills/receiving-code-review/SKILL.md)和社区 [Code Review Skill](https://github.com/mattpocock/skills/tree/main/skills/engineering/code-review)。这些材料提供操作方式与分析角度，并不构成使用 Agent 评审一定能发现全部缺陷的实验结论。

## 六、研究结论如何形成 `code-review-guide` Skill

[SKILL.md](../../../skills/software-engineering/code-review-guide/SKILL.md) 以准确评审对象为第一步，随后分别检查需求符合度和工程质量，最后报告可以定位与复核的真实发现。评审收到的反馈采用同样的证据原则处理。

| 研究认识 | Agent 的具体动作 | 对应文件 |
| --- | --- | --- |
| 不同 Git 状态对应不同评审对象（第一节） | 核对基准、工作区、暂存/未暂存及未跟踪文件 | [SKILL.md](../../../skills/software-engineering/code-review-guide/SKILL.md) |
| 需求正确性与工程质量不同（第二节） | 先按原始验收检查行为，再沿代码和测试检查专项风险 | [review-lenses.md](../../../skills/software-engineering/code-review-guide/references/review-lenses.md) |
| 审查意见必须可复现或明确限定（第三节） | 每项发现记录位置、触发、影响、证据与修复方向 | [review-lenses.md](../../../skills/software-engineering/code-review-guide/references/review-lenses.md) |
| 独立意见仍须技术核查（第四节） | 以当前需求、代码和相关测试判断接受或反驳 | [feedback-and-delivery.md](../../../skills/software-engineering/code-review-guide/references/feedback-and-delivery.md) |
| 评审授权不等于修改或发布授权（第一、五节） | 只读评审完成后交付发现，必要实施另按用户授权处理 | [feedback-and-delivery.md](../../../skills/software-engineering/code-review-guide/references/feedback-and-delivery.md) |

这样设计避免评审退化为格式评论，或不必要地扩展为自动修改、全套测试和合并操作。具体是否需要后续测试、架构修改或专项安全检查，由已发现的问题和用户任务范围决定。
