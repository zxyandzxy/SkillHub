# 可维护代码修改：变更范围、简单实现与必要说明

日常软件维护的大多数工作发生在已有系统里。工程师需要改变一项行为，同时保护与它相邻但不应变化的部分。代码审阅时经常出现两类相反问题：一类只追求少写几行，省去必要验证和错误处理；另一类利用小需求顺便统一目录、设计抽象层或增加配置开关。两者都可能降低维护性。

可维护代码需要让后续开发者理解此次修改解决了什么、为什么采取当前方式、哪些边界不能破坏，以及怎样确认它仍然正确。做到这些，不依赖固定的行数门槛或某一种代码风格。

## 一、从需求确定改动边界

进入代码前，应把用户要改变的外部行为与已有实现对应起来。修改一个查询过滤条件，看似只动一行 SQL，但如果调用方依赖了原来的排序或空值语义，真正的变更范围还包括测试和接口说明。反过来，顺手重命名无关模块并不会提高此次修复的正确性。

Google 的 [Small CLs 工程实践](https://google.github.io/eng-practices/review/developer/small-cls.html)倡导可理解、容易评审的小变更。这里重要的限定是“围绕一个清楚的目标”，不是一个提交最多修改多少文件。一个正确的变化可能必须跨界面、服务、数据库迁移和相关测试，应该把这些必需部分作为一个连贯增量交付。

例如修复上传功能没有检查文件大小的问题，必要改动可能包括服务端校验、前端错误提示、固定边界测试和使用文档。仅修改服务端返回值却不处理前端原有错误假设，可能使修复对用户不可见。另一边，把全部上传代码重构为插件平台，则必须有独立的结构风险或需求依据。

一项修改完成后，Diff 应当能说明每个变化与目标的关系。通常应清理自己引入的无用代码，避免混入全仓格式化；遇到任务外潜在问题，可以说明证据和位置，另外决定是否处理。对于用户未提交的修改或其他协作者的代码，不因为“不符合当前风格”就覆盖。

## 二、简单实现需要保留真实的边界处理

简单性是理解成本和变更成本的属性，不能只看代码长度。过多抽象会隐藏状态变化，导致读者跨文件追踪；过少抽象则可能让复杂规则和外部依赖混在一个函数中，难以测试和修改。

当一个规则已经在多个地方重复，或某个第三方服务需要独立管理重试与响应协议，增加函数或小模块可能减少整体复杂性，即使目前只有一个调用方。相反，假设将来会支持更多云平台而提前建立配置系统、工厂和扩展接口，并没有当前使用依据。Martin Fowler 的 [Refactoring](https://martinfowler.com/books/refactoring.html)提供了以结构改善支撑后续修改的系统方法；重构仍应有明确的行为保持要求。

错误处理也要按真实风险判断。用户输入、文件系统、网络和外部服务属于可能失败的边界，应有适当的检查、超时或明确错误传播。一个内部函数如果由已验证的不变量保证某项参数存在，就不必逐层添加重复判断；但对于无法证实的不变量，删掉校验会增加隐蔽失败。简单性不支持使用空 `catch`、静默返回默认值或吞掉故障状态来减少代码量。

例如为 API 调用添加失败回退时，应先问调用者能否接受旧数据、如何标记陈旧状态、重试是否可能重复执行副作用。若没有定义这些语义，给所有异常统一返回空列表或许让测试“通过”，却可能让真实错误被伪装成没有数据。

## 三、注释应该保存代码无法直接表达的信息

好注释首先说明非显而易见的约束。对于容易误解的边界条件，可以说明为何选择严格大于而非大于等于；对于外部协议可以记录字段单位与兼容限制；对于异常流程可以解释重试为何需要去重键。这些信息即使函数名准确，也不一定能从代码本身看出。

例如 `if retries < 3` 上方注释“当重试次数小于 3 就重试”没有增加信息。若项目依据外部服务额度和业务容忍时间确定三次上限，注释应说明这一约束或指向权威配置来源，避免未来维护者当成随意常量。

注释也有生命周期。接口改变时，旧注释和示例可能比没有注释更危险，因为它们看起来提供了权威解释。修改代码时应检查相关注释、配置示例及公共文档是否仍适用。版权和许可声明、构建指令或框架依赖的注释有独立用途，不能为“清洁代码”一律删除。

命名应表达业务含义与责任，而不是单纯越长越好。已有项目使用的稳定术语应保持一致；相同词如果表示不同概念，才需要明确区分。文件拆分按变化原因和理解成本决定，不能见到函数超过某个行数就机械拆分成许多只转发调用的碎片。

## 四、清理旧代码的风险来自不可见调用

搜索不到文本引用并不意味着函数没有外部使用者。框架路由、动态注册、反射、配置键、序列化字段、插件入口及第三方集成可能通过非字面路径调用代码。对公开 API 和配置项尤其需要考虑兼容承诺。

因此要区分两种清理：此次修改产生且已确认无用的临时变量或 import，可以随修改移除；原本存在的大量历史接口、脚本或生成文件，属于项目资产治理，删除前应确认引用、恢复来源和使用风险。后者应由专门的项目维护工作承担，而不是每次写代码自动进行全仓清理。

若重构涉及接口迁移，检查当前项目是否提供足够的兼容措施，例如保留旧入口并标记弃用、提供迁移说明或验证所有调用方。不要把“代码更短”当作足以突破已确认外部契约的理由。

## 五、可维护性需要通过具体检查体现

修改后检查两组问题。第一组关乎外部行为：关键输入、输出、失败边界和兼容关系是否符合需求，相关测试能否捕捉回归。第二组关乎理解和演进：模块职责是否更清楚，命名和注释是否准确，抽象是否反而增加路径复杂度，依赖与修改范围是否失控。

Google 的 [What to Look for in a Code Review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)涵盖设计、功能、复杂性和测试等问题。它的价值在于把代码质量落到可观察的项目行为上，而不是要求所有开发者使用同一套风格意见。

来自社区的 [Karpathy Guidelines](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/skills/karpathy-guidelines/SKILL.md)强调先确认问题、优先简单实现、控制修改范围和验证结果。这些是可吸收的实践提醒，但具体规则仍须结合代码已有约定；例如“问清所有不确定点”不应被误用成每个可查问题都停止实现。

## 六、研究结论如何形成 `clean-code-guide` Skill

[SKILL.md](../../../skills/software-engineering/clean-code-guide/SKILL.md) 先要求调查任务与真实调用，再围绕受限范围、简单实现、注释和清理组织编码自查。它面向正常编码与小规模重构，避免自动转成全面架构评审。

| 简单实现不等于最少代码行（第二节） | 根据当前约束选择抽象，保留真实故障边界处理 | [scope-and-simplicity.md](../../../skills/software-engineering/clean-code-guide/references/scope-and-simplicity.md) |
| 注释保存原因和约束（第三节） | 写明不变量、单位、外部协议与特殊处理理由 | [comments-and-cleanup.md](../../../skills/software-engineering/clean-code-guide/references/comments-and-cleanup.md) |

`clean-code-guide` 负责在具体编码中控制变更，`testing-guide` 负责测试有效性，`project-maintenance-guide` 负责长期资产治理。把这些职责分开，可以让普通代码修改保持轻量，同时在真正需要时加载更专业的方法。
