# 软件安全与隐私的工程判断：信任边界、控制措施与负面验证

软件安全问题并不只存在于加密算法和复杂攻击。一个普通的文件下载接口，如果只检查用户是否登录，却没有验证该用户是否有权访问具体文件，就可能泄露其他人的资料。一个功能即使使用了 TLS 和安全数据库，如果没有必要地收集联系人或把数据发送给外部服务，也可能存在隐私问题。

因此，安全与隐私需要从受保护对象和实际数据流出发。首先明确谁可以对哪些资源执行操作、哪里存在不可信输入与跨服务访问，再选择相应的技术控制和负面测试；个人数据的收集、共享、保留与删除还需要独立的隐私判断。

## 一、先识别资产、主体和信任边界

安全评估的起点是资产与操作。资产可以是用户文件、数据库记录、访问令牌、源代码、支付动作或系统配置。主体包括登录用户、匿名访问者、管理员、外部服务和本地进程。应明确哪些行为被允许、哪些访问不可信，以及违反边界会导致什么后果。

[OWASP 的威胁建模指南](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)介绍围绕系统组件、数据流和潜在威胁组织安全分析的方法。实践中不需要对每一处低风险修改建立庞大模型，但涉及跨用户对象、个人数据、支付或公网入口时，资产—边界—威胁—控制—验证的关系应该清楚可查。

例如用户请求 `/files/123` 时，服务器必须根据当前身份和文件的所有者、访问范围核查是否允许下载。URL 中使用随机 ID 只能增加猜测难度，不能替代授权。前端隐藏下载按钮也无法阻止直接构造 HTTP 请求。安全控制必须放在实际可信边界执行。

## 二、不同风险需要不同控制

认证确认主体身份，授权决定主体是否可以对某个对象执行特定动作；二者不能互换。输入校验检查数据是否符合业务或语法条件，参数化查询用于避免 SQL 注入，HTML 输出编码处理浏览器解释风险，路径限制防止越界访问文件。一个输入经过了格式检查，并不能证明它在所有使用位置都是安全的。

[OWASP Application Security Verification Standard](https://asvs.owasp.org/)（ASVS）为 Web 应用和服务提供可验证的安全要求。截至 2026 年 11 月，官网显示稳定版为 5.0.0。它可以帮助团队选择与项目相关的技术控制，但不能将完整 Web 安全清单机械套用到离线桌面应用。移动端有不同的客户端存储和平台权限问题，应参考 [OWASP MASVS](https://mas.owasp.org/MASVS/) 与实际操作系统规范。

安全控制还应遵守最小权限与安全默认。发现真实密钥进入源码仓库时，删除当前文件中的一行并不能消除已有提交、日志或外部复制中的泄露。需要评估暴露范围、撤销和轮换，必要时处理历史发布物。对第三方依赖的安全告警，应核对受影响版本、实际调用路径与修复方案；无差别升级所有包可能引入兼容风险，也不保证缺陷得到解决。

## 三、隐私关注整个数据生命周期

安全重点在防止未经授权的访问、篡改与泄露；隐私还关心处理个人数据是否必要以及怎样对待数据主体。例如某应用要求上传完整通讯录，只因为开发方便，就算传输加密和服务器访问控制都正确，也仍需要说明收集全部联系人是否服务真实用户目标。

[NIST Privacy Framework](https://www.nist.gov/privacy-framework)提供识别和管理隐私风险的结构。落实到具体功能，需要考察数据收集目的、最少必要字段、默认选择、共享范围、第三方服务、保留与删除策略、备份及用户控制。对接外部 AI 服务时还要确认哪些原始内容被发送、模型提供者如何处理输入、是否包含个人数据或未公开代码，以及用户授权范围是否覆盖该数据流。

加密保护部分传输和存储风险，但不能自动证明数据采集目的合理。脱敏与合成数据可以降低测试中的暴露风险，也不能使未经授权的真实数据外发变得合规。适用法律和组织级高风险接受应由有权限的专业人员决定，Agent 应提供事实与技术依据，不作没有审查的合规承诺。

## 四、验证安全需要检查拒绝路径

软件的正常使用测试通常证明某个被授权用户可以成功操作。安全还需要验证未登录、角色权限不足、访问其他用户资源、共享被撤销、恶意输入、秘密暴露及删除后的生命周期状态。对于对象授权问题，需要同时测试“访问自己文件成功”和“访问他人文件被拒绝”，并确认拒绝发生在可信服务端而不是仅在页面隐藏入口。

测试证据有不同等级。依赖扫描、静态检查、配置核查、实际接口负面测试和独立专业评审各有覆盖范围。扫描无告警不能证明不存在业务越权；测试覆盖少量请求也不能推出整个系统安全。关键结论必须对应实际运行的版本、环境和场景。

负面测试可能具有副作用，因此需要在安全且已授权的环境执行。不得擅自对生产数据做破坏性修改，或把真实用户信息提交给在线扫描器。无法验证的高风险路径应明确列出，不能为了完成报告虚构一次测试通过。

## 五、风险处理应按实际后果安排优先级

安全设计不需要为所有项目建立统一的大型审批流程。静态文案与局部配色修改通常只需检查没有额外泄露风险；跨用户对象访问、公网接口或敏感数据转移则需要更系统的边界分析和验证。优先处理能导致越权、敏感信息暴露或不可逆副作用的真实风险，而不是按扫描告警总数排列重要性。

[NIST Secure Software Development Framework](https://csrc.nist.gov/pubs/sp/800/218/final)将安全要求纳入软件开发过程。工程上的可行做法是让安全判断跟随受到影响的功能和数据边界，在设计、实现、测试与发布审查中保持同一套约定；不要求每次小修都产生完整威胁模型或合规报告。

安全风险可以被缓解、规避或在适当授权下接受，但应明确剩余问题和责任人。技术实现不能替代业务对数据处理目的、隐私承诺或重大残余风险的决定。
