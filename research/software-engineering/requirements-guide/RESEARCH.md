# 软件需求的形成：从用户问题到可验证行为

软件开发经常以一个方案开始：“增加一个提醒按钮”“接入云同步”“把列表改成卡片”。这些表述可以代表用户的真实想法，但尚未完整回答系统应解决什么问题、在哪些情境下生效，以及什么结果才算成功。需求工作的任务是理解用户目标和使用场景，分清事实、假设与决策，将它们转化为能够指导设计和验证的行为要求。

需求越复杂，直接根据一句话生成详尽规格越容易制造虚假的确定性。复杂产品可能隐藏关键取舍，而简单缺陷修复已有明确的目标和验收，不需要重复发起访谈。因此，需求处理强度应由真实歧义及其影响决定，而不是由文档模板或工具流程决定。

## 一、用户提出的方案与需要解决的问题

假设用户希望“增加每天的邮件提醒”。真正的问题可能是任务经常被遗漏，也可能是多人协同缺少截止通知。若直接把邮件视为不可更改的需求，就可能忽视通知时间、离线场景、隐私限制和用户是否希望其他渠道。需求分析应先问清使用者在哪个工作流程遇到什么困难，再讨论邮件是否合适。

[ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)介绍系统与软件需求工程的过程和要求。标准关注需求的发现、分析与表达，并不要求每次微小改动生成同等复杂的文档。需求规格能否发挥作用，取决于它是否真正把相关人员的目标与可验证的系统行为联系起来。

还应防止把现有实现误当作真实需要。旧代码显示系统只存储一个联系人，可能是历史限制，不等于用户只需要一个联系人。代码回答的是“系统当前怎样工作”，用户与业务规则回答的是“系统应该怎样工作”。二者冲突时需要调查并作出明确决定。

## 二、事实、证据、建议与决定应区分

需求中的信息具有不同来源。用户说希望离线使用，这是直接需求表达；从现有数据库观察到某字段可为空，是实现事实；认为用户会喜欢某种布局只是设计假设；产品负责人明确选择一项行为才是已确认决定。将这些信息混合，容易在后续设计与测试中制造未经授权的承诺。

真实用户证据可能来自访谈、观察、使用日志或已明确的业务流程，但要记录样本和条件。如果没有收集真实用户证据，就不应把开发者或 Agent 的想法包装成“用户普遍需要”。[GOV.UK 的用户研究指南](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)强调从用户任务和观察出发理解需要，这对任何以用户为中心的软件都有参考意义。

Agent 自主调查的边界也应清楚。能够在项目文档、接口、设计图和代码中查明的事实，应先查明；会改变商业目标或用户行为的选择仍由有权限的人决定。技术上能实现一个功能，也不代表它已得到产品授权。

## 三、提问顺序取决于决定之间的依赖

需求访谈并非尽可能提出更多问题。真正有价值的提问能消除足以改变后续设计的歧义。以一个离线账本为例，首先需要确认数据是否必须保存在设备本地。若答案是必须离线，用户身份、云同步、合并冲突和第三方数据存储可能都不是当前范围；若答案允许同步，后续才需要讨论这些问题。

因此，访谈可以根据决定依赖建立顺序，先解决限制下游选择的前提。每轮提出当前最重要的一个问题，解释答案会改变什么，并给少量具体选项与推荐理由。重复询问已经确认的事项会增加用户负担，也容易让已决定的范围重新变得模糊。

低风险、可撤销且不改变用户体验的细节不必都等待审批。例如在已有框架内选择一个内部辅助函数名，并不需要再次请求产品确认。高影响行为、数据迁移、隐私边界和重大成本则需要明确决定。用户暂时没有回答时，应保留未决项，不把沉默理解为同意。

如果一个交互方案很难从文字判断，可以使用小型可丢弃原型，让用户比较实际状态。原型帮助形成选择，却不能把参与人的即时反应直接推广为真实用户群体的研究结论。

## 四、从场景转为可验收的结果

需求如果只写“性能良好”“支持离线”“界面简单”，测试者无法知道什么行为应该发生。应将关键要求转换为具体场景：前提是什么，用户做什么，系统应给出什么可观察结果。

例如，假设规则已明确为“金额达到 100 元免运费”。验收需要说明 99 元、100 元和 101 元的对应结果，特别是边界是否包含 100 元。这个数字是说明方法的假设例子，不代表任何真实产品的规则。关键原则是：预期应从已经确认的业务定义推导，不能通过调用待实现的生产函数生成期望值。

[NASA 的 How to Write a Requirement](https://www.nasa.gov/reference/appendix-c-how-to-write-a-requirement/)讨论要求表述的清晰性与可验证性。实践中还需要检查行为是否必要、一致、可行和可追溯。一个看似具体的目标，例如“首页必须在一秒内加载”，如果没有说明设备、网络和测量场景，仍可能无法公正验收；Agent 不应凭个人经验把这一阈值写成已批准的产品要求。

## 五、范围控制和需求变更

完整需求并不等于覆盖所有假想情况。明确本轮必须实现、可以延后和不做的行为，能够防止 Agent 将普通需求扩展成庞大系统。数据和失败规则也只需覆盖当前真实业务风险，例如重复保存、非法输入或重启后的持久状态，而不是机械加入登录、权限、云同步和复杂分析平台。

需要多阶段实现时，需求可以按用户可感知的能力拆分，并保持验收目标稳定。后续出现新证据时，只更新受影响的规则及相关设计和测试；已经确认但仍有效的内容无需重开讨论。已有实现不能固化错误需求，同样也不应为了引入一项新要求而否定全部已有决定。

需求文档可以短，也可以长。清楚的小修复在对话中形成范围与验收条件即可；长期项目则复用已有的产品说明和规范，避免同一事实散落在多个互相冲突的文件中。

## 六、从需求研究到 `requirements-guide` Skill

需求的核心顺序是“理解现有事实与用户问题 → 消除关键歧义 → 给出可验收的行为”。[requirements-guide Skill](../../../skills/software-engineering/requirements-guide/SKILL.md) 按这条顺序约束 Agent，重点防止自行扩张需求或把实现反推为正确答案。

| 研究认识 | Agent 的具体动作 | 规则文件 |
| --- | --- | --- |
| 用户方案不总是完整目标（第一节） | 查明用户场景，分清要求与既有实现 | [SKILL.md](../../../skills/software-engineering/requirements-guide/SKILL.md) |
| 证据和决定具有不同权威（第二节） | 标记事实、假设、建议及已确认取舍 | [SKILL.md](../../../skills/software-engineering/requirements-guide/SKILL.md) |
| 提问应当依照决定依赖（第三节） | 优先澄清最影响后续设计的问题，不重复已回答事项 | [decision-interview.md](../../../skills/software-engineering/requirements-guide/references/decision-interview.md) |
| 验收应从业务规则独立得出（第四节） | 用前提、操作、结果和依据表达关键场景 | [acceptance-and-traceability.md](../../../skills/software-engineering/requirements-guide/references/acceptance-and-traceability.md) |
| 范围要与真实风险相称（第五节） | 小任务直接收敛，需求改变时只调整受影响部分 | [SKILL.md](../../../skills/software-engineering/requirements-guide/SKILL.md) |

该 Skill 负责形成可确认、可检验的需求；模块边界与架构取舍交由 `design-guide`，测试用例与执行证据交由 `testing-guide`。让三个阶段引用同一组已确认规则，可减少在需求、实现和验收之间反复定义同一事实。
