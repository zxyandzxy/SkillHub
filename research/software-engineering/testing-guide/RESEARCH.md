# 软件测试的可信度：独立预期、故障发现能力与真实验收

自动化测试可以非常快地给出“通过”，但它能说明什么，取决于测试如何定义正确结果、实际经过哪些组件，以及断言是否能够发现所关心的错误。对于由 Agent 同时编写实现和测试的软件，最大的风险之一是把同一个错误理解复制进两处代码，再通过测试得到看似可靠的结论。

测试设计应从已确认的外部行为出发，建立独立的预期，选择能够观察该行为的执行方式，并准确说明测试证据覆盖到哪里。测试框架、用例数量、覆盖率和命令退出码都是辅助手段，不能代替这一逻辑。

## 一、正确结果必须有独立依据

测试预期（test oracle）是判断一个输出正确与否的依据。对业务规则明确的功能，预期可以直接来自需求或规则文本；对计算功能，可以来自独立手算、已验证基准或数学性质；对界面功能，可以来自已确认的用户操作和可观察状态。

设想一个运费规则：订单金额达到 100 元免运费，低于该数值收取 10 元。这里 99 元、100 元、101 元是有明确区分能力的边界测试。其正确输出要由已确认的“达到”含义推导，不能用待测函数的返回值生成 expected。如果需求只写“满一定金额”，金额与边界条件仍是未确定业务规则，测试作者不能自行决定为 100 元再以测试通过证明需求已满足。

当 Agent 编写实现和测试时，可以由同一个 Agent 完成两项工作，但预期数据必须有独立来源。必要时先从需求整理黑盒场景，再阅读实现寻找遗漏。换一个 Agent 来写测试可能带来不同视角，仍不保证它没有沿用相同的错误需求理解。独立性关键在证据来源，而不在模型实例数量。

对于无法建立唯一答案的问题，可使用性质测试、变形测试、领域专家判断或受控人工验收，但要说明采用哪种替代判定方式以及它无法覆盖的风险。不能因为缺少 oracle，就悄悄退化为“程序没有报错便算正确”。

## 二、测试是否有能力发现真正的错误

断言的质量比运行次数更重要。一个订单查询测试只检查返回数组非空，即使结果顺序错误、权限过滤失效或关键字段缺失，也可能通过。对重要场景需要验证确切结果、状态改变和必要副作用，包括正常输入、边界值、非法条件与失败后的恢复。

内部结构的白盒分析适合发现未走过的分支、状态转换和异常路径；从外部接口出发的黑盒测试能检查用户真正看到的结果；集成测试则检验多个组件组合后是否遵守数据契约。三者职责不同，可以按任务风险组合使用。不要求每次小修改全部补齐每一层，但高风险的关键连接不应完全依赖 mock。

例如服务端导出 API 的测试使用 mock 数据仓库，可能证明服务层调用了正确方法，却不能验证真实数据库的过滤条件，也不能证明 CSV 编码符合下载客户端要求。对于这些真实连接，需要合适的集成或端到端检查。 [Google 的 Test Behaviors, Not Methods](https://testing.googleblog.com/2014/04/testing-on-toilet-test-behaviors-not.html) 体现了把测试重点放在可观察行为的思路；具体需要哪一层测试仍取决于系统结构。

覆盖率可以用来定位完全没有执行的代码区域，但高覆盖率不能说明断言具有正确性，也不能说明需求场景已完整覆盖。变异测试通过对代码作受控变化检查测试能否发现错误，[Google 的相关研究](https://research.google/pubs/long-term-effects-of-mutation-testing)展示了其工程价值。变异测试有实际成本，适合对关键逻辑按风险使用，而非成为所有微小修改的固定门槛。

## 三、从测试执行到验收结论存在多个层次

构建成功、单元测试成功、集成运行成功、真实用户任务完成，是不同性质的证据。一项 UI 功能的截图只说明某个静态状态，不能证明用户点击后状态正确；某个后端接口通过 mock 测试，也不能证明真实外部服务接受其请求。

设计测试时可将重要需求对应到一组有限的可观察证据：需求或验收条件、测试输入、独立预期、执行入口、实际输出。这个关系可以写在测试或简短交付说明中，不要求每个项目都维护庞大的矩阵文档。证据应能直接回答“用户要求的行为是否发生”。

测试环境会影响证据解释。时区、随机种子、网络状态、依赖服务版本和共享测试数据都可能使结果不稳定。对于等待条件，应优先轮询可观察状态而不是固定睡眠若干秒；跨服务测试还要隔离和清理自身产生的数据。测试运行前要确认服务、成本与数据修改属于当前授权范围。

若命令退出 0，需要确认关键测试实际收集并执行，没有被过滤或跳过。若测试失败，应说明失败来源是新修改、原有基线、环境或尚不明确。证据对应某个代码版本与测试环境；后续修改影响原结论时重跑相关检查，未影响时不必为形式上的完整性重复全量运行。

## 四、测试驱动开发与验收的适用条件

测试驱动开发（TDD）通过先定义一个可观察行为的失败测试，再实现最小满足行为的代码、进行必要重构与复验，帮助开发者限制当前实现目标。它有适用前提：行为可表达，预期可靠，测试反馈时间与任务相称。

调试时先复现缺陷，能为修复建立明确回归依据；如果故障只在真实设备或难以自动化的外部系统出现，则应保留可重复的人工步骤及证据，不为了强制 TDD 而人为编造单元测试。简单文案修改也不必为满足流程而新增无信息测试。

ISTQB 的 [Foundation Level](https://www.istqb.org/certifications/certified-tester-foundation-level) 材料可以帮助核对测试基础概念和设计方法，但它并不要求所有 Agent 开发任务采用统一模板、覆盖率阈值或用例数量。

最重要的判断是：本次测试是否能发现用户真正担心的问题，实际结果能支持多大的完成声明。若无法验证，就明确说明未覆盖的条件，而不是用更好看的测试报告替代真实验收。

## 五、研究结论如何形成 `testing-guide` Skill

[SKILL.md](../../../skills/software-engineering/testing-guide/SKILL.md) 从需求及独立预期开始，再按风险确定测试视角，最后根据实际运行证据报告完成状态。它将测试设计与执行检查放在同一工作流中，避免只生成用例而不检查其可执行性。

| 测试需要发现真实错误（第二节） | 检查精确断言、边界、状态、副作用和必要集成连接 | [oracles-and-cases.md](../../../skills/software-engineering/testing-guide/references/oracles-and-cases.md) |
| 不同测试层级证明不同事实（第三节） | 将每项检查与对应版本、环境和需求场景关联 | [evidence-and-verification.md](../../../skills/software-engineering/testing-guide/references/evidence-and-verification.md) |
