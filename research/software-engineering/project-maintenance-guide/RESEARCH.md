# 长期软件项目的资产维护：权威文档、测试价值与安全清理

软件项目在反复迭代后会积累文档、测试、诊断脚本、生成文件和历史设计。维护者经常会遇到多份相互矛盾的说明，或大量看似过时却不敢删除的文件。处理这些资产需要同时考虑当前使用价值、依赖和可恢复性。文件数量下降可以是清理的结果，但不能单独说明维护质量提高：删除仍在提供独立验证的测试，可能比保留几份过期笔记更危险。

这类工作应由明确触发事件发起，例如接口迁移完成、重复文档产生冲突、CI 成本异常、临时实验结束或准备公开发布。每次选择可核对的范围，避免把一次功能修复变成无边界的全仓整理。

## 一、判断资产价值应先理解它承担的任务

一份文件是否值得保留，首先取决于谁使用它、在哪个入口使用、其内容是否可信，以及删除后会失去什么。相同的“README”名称可能对应完全不同的职责：一份说明如何安装，另一份解释架构形成背景。若只按文件名、大小或修改日期判断，就会错把历史证据当成使用指南，或把仍需保留的决策记录删掉。

对文档、测试、脚本和生成产物，可以分别询问其权威来源和调用链。文档要核对真实命令、API 和用户任务；测试要核对覆盖的可观察行为和实际执行位置；脚本需要核对 CI、包管理器、运维手册和人工使用入口；生成产物要明确是可重新生成的缓存，还是发布包本身。

例如仓库里同时有 `docs/install.md` 和 `README.md` 的安装段落，一份包含旧依赖，另一份使用当前命令。维护者应先在当前代码和实际环境中验证安装路径，再确定哪份是权威入口；让重复说明引用它，而不是任选一份删除或把两段拼成新的未经验证步骤。

## 二、文档治理：减少冲突来源，保留必要解释

[Diátaxis](https://diataxis.fr/) 将文档按教程、操作指南、参考和解释四种用途区分。这种分类是诊断材料职责的方法，不能机械要求每个仓库创建四个目录。小工具可能只需一个 README；复杂项目则可能需要独立 API 参考和架构解释。

文档的权威性来自与现实的持续同步。启动方式发生变化时，应更新用户真正访问的安装入口；API 发生变化时，应修改对应参考与示例；设计方案改变时，应让当前规范指出新决定。若过去的架构决策仍有解释价值，保留记录并标明被替代状态，帮助后来者理解为什么放弃原方案。把旧结论改写成“当时就知道新方案更好”会损坏历史因果信息。

《[Software Engineering at Google](https://abseil.io/resources/swe-book/html/ch10.html)》中关于技术文档的讨论将文档视为需要维护的工程资产；由此可推导的维护要求是识别读者、用途及更新入口，而不只是提高 Markdown 数量。对每个发布版本可以选择少量真实有效的示例，验证命令和链接可用；不要求每次改一个变量都重写全部文档。

## 三、测试资产的独立价值与维护成本

测试数量增加通常意味着维护成本增加，但不能因此把运行较慢或偶发失败的测试直接删掉。判断测试价值需要知道它是否检查独立的预期、能否发现某类实际错误，以及其它测试是否能提供相同信心。

例如某集成测试需要真实数据库，运行较慢，却验证了 ORM 映射、事务和约束在组合使用时的行为。把它替换成全部 mock 的快速单元测试，可能丢失这一层证据。合理的选择可能是把数据库测试放进合适的 CI 阶段、改进数据隔离，或减少高度重复的路径，而不是宣布“速度提升了”便算维护成功。

对 flaky（不稳定）测试，应调查时间、随机数、共享状态、顺序依赖和环境条件。暂时隔离可作为处理办法，但需要说明该测试保护了什么、隔离造成什么证据缺口、恢复条件是什么；隔离不等于问题已解决。 [Software Engineering at Google 测试章节](https://abseil.io/resources/swe-book/html/ch11.html) 和 [Martin Fowler 的测试金字塔讨论](https://martinfowler.com/articles/practical-test-pyramid.html)都强调不同测试层级承担不同价值。测试金字塔不能被简化成按数量比例删除集成或端到端检查。

## 四、脚本、实验与生成产物的生命周期

脚本是否属于正式工具，取决于是否具有稳定、重复的用途。一次性定位问题的日志提取脚本可以在任务结束后清理，但若某个分析步骤需要反复复现，应保留其调用方式、依赖、输入格式和预期输出。清理操作前要检查是否在 CI、发布流程或人工 runbook 中被调用，普通文本搜索未匹配也不能说明它没有使用者。

生成产物的处理更依赖发布与复现条件。自动生成的临时构建目录通常可以忽略或重新生成；发布给用户的预编译文件可能必须进入版本或发行包；某些研究实验结果不能轻易重算，虽然由脚本产生，也可能有长期保存价值。

`.gitignore` 只是影响 Git 对未跟踪文件的识别，不会让已经被跟踪的文件自动从版本中消失。[GitHub 的忽略文件说明](https://docs.github.com/en/get-started/git-basics/ignoring-files)可以核对具体行为。整理时还要区分本机秘密配置、可共享的无秘密配置模板和运行中生成的缓存，不能为了让仓库“干净”误删恢复线索或用户未提交工作。

## 五、安全删除是一项需要证据的变更

删除之前至少应检查：调用方、构建或发布配置、动态注册、反射或插件机制、外部使用者、未提交改动以及是否有真实可靠的恢复来源。对数据迁移和公开接口尤其如此。没有可靠的回滚能力时，应优先保留、标记为被替代或进行小范围迁移。

例如仓库的一份配置文件已经不被直接 import，但部署脚本通过约定名称读取它。单纯 `grep` 找不到函数引用无法发现这一依赖。删除后可能只在真实部署中失败。更可靠的处理是确认入口、模拟使用环境并运行相关检查；必要时先把读取逻辑迁移到新位置，验证通过后再删除旧文件。

资产处理可归为保留、更新、合并、归档、隔离与删除。每一种都有适用条件：当前有价值且可信则保留；用途仍在但内容过期则更新；两处事实冲突则定位权威版本并合并；历史决策可归档；暂时无法执行的重要测试可隔离；只有在依赖与恢复风险确认后才能删除。

在执行规模上，从证据充分、风险较低的目标开始。每个小批次检查相关构建、链接、脚本和测试，不因为“总文件数下降”就忽略功能入口是否还可用。若清理会涉及未经授权的发布或删除范围，应报告需要决定的具体影响，不能自行扩大权限。

## 六、研究结论如何形成 `project-maintenance-guide` Skill

[SKILL.md](../../../skills/software-engineering/project-maintenance-guide/SKILL.md) 将资产维护分成范围盘点、价值与归属判断、分类处理、安全迁移和变更后验证。它强调以真实使用关系作决定，不依据日期、名称或单次失败删除资产。

| 研究认识 | Agent 的具体动作 | 对应文件 |
| --- | --- | --- |
| 资产是否有价值取决于读者和调用方（第一节） | 核对用途、权威性、真实依赖和删除后损失 | [SKILL.md](../../../skills/software-engineering/project-maintenance-guide/SKILL.md) |
| 不同文档承担不同读者任务（第二节） | 建立权威入口并消除相互冲突的重复事实，保留被替代决策的历史 | [docs-and-tests.md](../../../skills/software-engineering/project-maintenance-guide/references/docs-and-tests.md) |
| 测试数量和速度不能代表独立信心（第三节） | 检查被覆盖的行为、测试层级、可靠性及失去测试的风险 | [docs-and-tests.md](../../../skills/software-engineering/project-maintenance-guide/references/docs-and-tests.md) |
| 生成文件有不同发布与复现用途（第四节） | 按实际生命周期处理脚本、产物、忽略规则和配置 | [safe-migration.md](../../../skills/software-engineering/project-maintenance-guide/references/safe-migration.md) |
| 隐藏入口会使删除存在回归风险（第五节） | 核对动态使用、CI、外部依赖与恢复来源，再小批迁移和验证 | [safe-migration.md](../../../skills/software-engineering/project-maintenance-guide/references/safe-migration.md) |

局部编码产生的无用 import 或临时变量仍应在编码任务内清理；只有涉及历史资产的系统性维护才触发这一 Skill。这个边界让项目能够按需治理长期负担，而不把每次功能开发升级为全仓清理。
