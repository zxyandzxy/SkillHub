# 软件系统设计：从真实需求到可维护的架构边界

软件设计的难点经常出现在功能和实现之间：需求描述了用户希望完成的行为，代码却必须把这个行为分配给模块、接口、数据结构和运行状态。一个设计在纸面上看起来层次完整，不意味着真实代码能遵循它。评估设计时，首先应检查它能否解释系统中谁负责什么、信息如何流动、失败如何处理，以及将来改变一个需求时哪些位置需要一起调整。

系统设计也有经济性。设计不足会使职责不清、数据被多个组件任意修改；过度设计则把尚未出现的变化变成额外配置、抽象和协调工作。因此设计过程需要先确认当前问题的大小，再决定需要多少设计活动。

## 一、从正在运行的系统确认设计边界

### 需求与现有实现分别提供什么信息

需求说明应当发生的行为，实际代码说明目前能够发生的行为。二者可能矛盾：设计文档写明请求经过统一服务验证，但新功能可能直接访问底层数据库；README 给出一个入口，实际生产环境可能使用另一条路由。若不核对现场，后续设计就会建立在过时的依赖图上。

调查应沿一个真实业务流程展开。例如新增订单导出功能，先确认导出请求从哪个 API 或 UI 入口进入、查询逻辑由谁实现、哪些数据需要权限过滤、文件写入在哪里完成、错误如何返回、谁负责临时文件清理。这个调用路径能帮助识别必须修改的职责边界。只看文件夹名或抽象层图，容易错过绕过公共接口的真实依赖。

对现有架构的调查可以先回答四个问题：模块承担什么职责；数据所有权在哪里；依赖应向哪个方向流动；哪些约束已经被调用方依赖。循环依赖、业务规则重复、绕过接口访问内部状态，都是值得检查的信号；是否需要调整，还应判断它们是否真实增加错误、理解或修改成本。不能看到一个 `utils` 目录就推断架构已经失效。

### 从数据所有权推导模块边界

模块边界不等于文件边界。一个模块可以跨多个文件，也可能只有少量代码。界定边界更有效的依据是某类业务规则由谁负责、谁允许修改状态，以及变化是否需要经过多个毫不相干的组件。

例如，一个购物车价格由前端界面、订单服务和数据库触发器分别计算，会形成多份可能漂移的规则。设计时应明确价格计算的权威位置，并约定其他组件如何获得结果。如果需要缓存或复制数据，应定义更新和失效语义，而不是让三个位置各自维持一个“看起来一致”的版本。

架构决策应同时考虑现有代码迁移的成本。为隔离第三方支付服务创建明确的接口，可能确实能降低测试和替换风险；为只增加一个报表格式而先建通用插件平台，则往往缺少当前需求的依据。简单方案是满足真实约束的最少必要结构，不是机械压低类数、目录数或代码行数。

## 二、比较方案应关注会改变结果的差异

设计备选值得比较，是因为不同方案会改变关键质量属性、迁移代价或使用行为。若两套设计只是类名不同、没有实质不同的操作语义，长篇比较不会产生新的判断。

一个有用的方案说明应包含：真实输入和输出、数据存储与所有权、失败后的状态、兼容方式、重要性能或成本条件，以及验收观察点。假设把同步导出改成后台导出：它可能降低请求超时风险，却增加任务状态、重试、重复执行和过期文件清理问题。此时方案比较应集中于这些实际后果，而不是泛谈“同步架构与异步架构哪个更现代”。

SEI 的 [Architecture Tradeoff Analysis Method](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/) 强调架构取舍必须围绕质量场景。这里可吸收的原则是让架构决策接受场景检验；完整 ATAM 的人员、会议和步骤并非每个小项目都需要。重要、难以撤销的结构性选择可以记录轻量架构决策记录（Architecture Decision Record，ADR），包括背景、实际备选、选择原因和后果。[Google Cloud 的 ADR 指南](https://docs.cloud.google.com/architecture/architecture-decision-records)提供了可参考的记录方式。普通变量命名或局部函数拆分不必留下 ADR。

当架构约束能被机器明确判断时，可以利用项目生态中的检查工具阻止新增违规。例如 Java 项目可以借鉴 [ArchUnit](https://www.archunit.org/userguide/html/000_Index.html) 对依赖方向设定规则；其他语言可用相应的静态分析或测试。规则应服务于确实重要的边界，不能为了增加检查数量而另建复杂治理系统。

## 三、让设计能够沿真实路径验收

纯文字图可以帮助理解组件关系，但无法证明它能满足用户任务。设计应能被一条完整流程穿透：用户输入进入哪个接口、经过哪些验证、由谁修改状态、怎样生成可观察结果；失败或取消时数据会处于什么状态。这样的端到端追踪同时提供实现任务拆分依据。

以前述后台导出为例，先实现一条简单路径：创建任务、后台读取授权数据、写出文件、用户获取结果；随后补充真正需要的失败和取消语义。若任务因网络错误重试，必须明确是否可能生成重复文件或重复通知。实施计划按可验证行为组织，而不是把“创建类”“添加数据库表”“编写控制器”分别当作需要用户审批的里程碑。

[DORA 的小批次实践](https://dora.dev/capabilities/working-in-small-batches/)支持保持变更可集成、反馈及时的工程方向。对长期任务可以维持项目目标、里程碑、依赖、当前批次四种信息职责；它们可以由已有文档承载，无须每层强制创建一个 Markdown。把全部未来任务详细排满往往导致计划很快失效，近期重要依赖反而难以识别。

涉及多个 Agent 并行时，设计边界还要能承担工作隔离。接口、数据模型和验收尚不确定时，多 Agent 同时修改核心文件可能制造比节省的执行时间更多的冲突。只有输入、输出、修改范围和集成责任明确，才适合并行；否则由一个 Agent 完成连贯增量更容易保持一致。

## 四、判断何时需要重新设计

结构性修改有成本，不能只因代码不符合某个理想模式就开始重构。应观察当前设计是否阻碍已确认需求：接口变更需要大量不相关调用方同时修改，业务规则无法保持一致，单一变动多次造成跨组件回归，或故障无法沿已有边界隔离。证据充分时，优先调整受影响的最小结构。

设计和实施过程中可能发现原来的假设不成立。例如原设计认为导出不触及敏感数据，调查后发现包含受限用户信息。此时需要重新确认权限和数据流边界；这种变化会影响用户目标和风险，不能作为普通内部重命名处理。若只是新发现现有代码已有一个可复用的导出帮助函数，则可以在原授权范围内调整实现方案。

采用新结构后应更新受影响的接口说明、架构图或 ADR；历史决定被替代时保留旧决策背景和新决定的位置。这样后续维护者才能区分当前约束与过去的选择。具体实施仍需要测试、代码评审及真实运行证据，设计完成不等于实现已经符合设计。

## 五、来源与适用范围

上述方法主要参照 [SEI 架构取舍研究](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)、[Google Cloud ADR](https://docs.cloud.google.com/architecture/architecture-decision-records)、[ArchUnit](https://www.archunit.org/userguide/html/000_Index.html)、[DORA Small Batches](https://dora.dev/capabilities/working-in-small-batches/) 和 [OpenAI 长周期 Codex 工程案例](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)。这些来源分别讨论质量属性取舍、决策记录、可执行架构规则、小批集成和长期任务状态管理，不能据此断言某一种模块分层一定提高所有项目的质量。

## 六、研究结论如何形成 `design-guide` Skill

[SKILL.md](../../../skills/software-engineering/design-guide/SKILL.md) 将研究中的设计判断组织成三段任务：调查真实现场、形成边界明确的方案、拆为可验证实施增量。关键步骤按任务风险调整，简单局部修改可以跳过完整架构讨论。

| 研究认识 | Agent 执行动作 | 对应文件 |
| --- | --- | --- |
| 纸面架构与真实依赖可能不同（第一节） | 沿入口、调用和数据所有权调查，不凭文档猜模块关系 | [SKILL.md](../../../skills/software-engineering/design-guide/SKILL.md) |
| 模块以职责、状态和变化边界划分（第一节） | 记录重要接口、数据所有权、依赖与失败行为 | [architecture-and-decisions.md](../../../skills/software-engineering/design-guide/references/architecture-and-decisions.md) |
| 比较方案需要明确质量属性和后果（第二节） | 只比较会影响成本、兼容或长期约束的实际备选；必要时记 ADR | [architecture-and-decisions.md](../../../skills/software-engineering/design-guide/references/architecture-and-decisions.md) |
| 实施需要尽早形成可观察结果（第三节） | 以完整用户行为为增量，声明依赖、验收和集成影响 | [incremental-planning.md](../../../skills/software-engineering/design-guide/references/incremental-planning.md) |
| 多 Agent 并行需要可隔离边界（第三节） | 缺乏稳定接口时先串行推进，有独立接口和验收再并行 | [incremental-planning.md](../../../skills/software-engineering/design-guide/references/incremental-planning.md) |
| 只有重大结构变化需要正式取舍（第四节） | 将普通重构留在实现任务，不为每次小改创建 ADR 和方案矩阵 | [SKILL.md](../../../skills/software-engineering/design-guide/SKILL.md) |

该 Skill 的主要交付是设计方案或实施计划；需求澄清、代码编写、测试和 UI 视觉设计继续由相应任务负责。这样能使设计保持足够的专业判断而不变成所有开发任务必须经过的固定审批流程。
