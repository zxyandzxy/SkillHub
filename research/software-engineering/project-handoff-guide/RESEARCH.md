# 长周期软件任务的可靠交接：真实现场、持久状态与上下文恢复

复杂开发任务可能持续数小时、数日或跨越多个 Agent 会话。对话记录中出现过的决定和进度不一定仍然适用于当前工作区：某个分支可能更新、测试结果可能过期，未提交文件可能属于其他协作者。可靠交接的目的，是让接手者用少量必要信息恢复任务，知道哪些决定仍有效，实际完成了什么，以及下一步能从哪里安全继续。

若只保存一段“已经做得很好、接下来继续开发”的摘要，接手者无法判断它是否对应当前代码。这类摘要看似完整，却常导致重复实现、覆盖现有修改或错用旧结果。可靠的任务状态必须独立于单轮对话，并能够对照真实项目材料核查。

## 一、目标、决定、计划与现场是不同类型的信息

软件项目通常至少存在四类重要信息。需求说明定义最终应达到的行为与验收；设计文档记录系统如何组织和重大方案为何被选择；执行计划说明任务依赖及阶段目标；当前快照记录实际进度、验证和阻塞。这些职责可以存在于少量文件中，但不能互相替代。

Git 历史提供已提交的版本变化，工作区则包含未提交、暂存和未跟踪的现场内容。进度快照可以引用这些信息，但不能证明文件确实存在或测试确实在当前版本通过。一个“已完成接口 A”的记录，需要对应实际分支、提交或文件检查才能被恢复者信任。

[OpenAI 关于长周期 Codex 任务的工程文章](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)讨论外部化任务状态和可验证阶段成果的价值。[Anthropic 关于长任务 Agent 的研究](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)也强调跨上下文保持可读、可检查的工作状态。对普通开发任务的启示是保存恢复所需的事实，而非保存完整会话所有文字。

## 二、快照应聚焦恢复工作所必需的信息

一个可恢复快照应清楚说明任务身份、目标和非目标、已确认的技术与产品决定、已实现与未实现部分、Git 状态、实际验证、调查结论、阻塞条件和下一项可以执行的动作。若有特殊服务、临时测试环境或实验数据，还需要说明它们的位置、归属和是否可安全清理。

快照需要区分状态。用户已经批准的实现范围、Agent 仅提出的建议与仍需产品决定的取舍，不能混写为“已确认方案”。如果只完成代码实现而没有运行相关测试，也应准确报告“已实现，待验证”，而不是把完成状态写成“已通过”。

长期项目不需要每次工具调用都记录进日志。值得保留的是会改变后续选择的事实，例如某错误被证实来自配置传递、某实验排除了特定假设、某次架构决定由新的需求替代。机器可重新获取的大量日志可以保留在原位置并以链接引用；复制整个终端输出只会加重后续阅读负担。

## 三、接手时必须重新识别任务与代码版本

设想快照记录：“分支 feat/guide 的新导航已经通过测试”，但接手时工作区已经切换到 main，远程主分支还包含其他修改。若直接依据快照继续编辑，可能把测试结论错误地套在不同代码版本上。接手者应先确认当前目录、目标分支、最近提交、未提交/暂存/未跟踪内容，再判断之前的计划是否仍对应当前现场。

还要核对测试的“新鲜度”。如果自上次测试以来，只修改了不影响该功能的文档，无须为交接机械重跑全部测试；如果接口、依赖或配置已经改变，旧通过记录就不能证明新的状态。正确做法是识别受影响范围，仅重跑会影响后续行动判断的检查。

对于复杂故障或科研实验，接手者还应核对原始数据、配置和运行结果。摘要中的“实验完成”可能是计划状态，也可能只表示部分命令成功；应回到具体结果及失败状态判断是否可继续。

## 四、交接与上下文压缩的关系

对话上下文压缩是一种运行框架能力，可能保留部分语义但省略细节。跨会话的 Markdown 快照则是人和 Agent 都可以查看的外部记录。二者作用不同：压缩服务当前模型上下文，快照服务任务持久性。不能假定新 Agent 还能读到旧模型的内部压缩状态，更不能把不可见的压缩结果当作唯一事实来源。

长任务中也可能使用子 Agent 并行处理独立工作。如果任务拆分具有清楚接口、不同工作区和验收责任，交接快照可以记录每个独立成果及集成状态；如果多个 Agent 修改相同核心文件，而没有稳定版本和协调机制，单纯增加参与者可能使交接更加复杂。

交接本身不意味着必须离开当前会话。任务正在顺利推进时，不需要频繁制造快照打断实施；达到重要阶段、准备换 Agent、存在大量未提交内容或状态可能失效时，持久记录的价值才更高。

## 五、退出任务时留下可以直接执行的下一步

交接的完成条件不是生成一份漂亮报告，而是接手者能够判定如何安全恢复。下一项动作应说明目标、入口、依赖和必要检查，例如“在已确认的分支上补齐支付超时场景的集成测试，使用测试环境的合成订单”。“继续优化代码”没有足够的恢复价值。

在半成品状态中断时，应说明哪些文件已修改、哪些问题阻塞、是否存在临时资源和哪些结果未经验证。写入快照的权限仍需谨慎：前一个 Agent 建议“下一步发布”，不等于用户已经授权推送或公开；交接也不自动许可删除、重置工作区和改变其他协作者文件。

需求或架构历史具有长期解释作用，但应指向当前生效的规则；旧决定被替代时保留时间与原因，防止读者把过去的选择当成现在的要求。保持信息职责清楚，能使工作区与文档在长期维护中互相校验。

## 六、从任务恢复研究到 `project-handoff-guide` Skill

上述研究形成“保存必要事实 → 对照真实现场 → 恢复已授权任务”的流程。[project-handoff-guide Skill](../../../skills/software-engineering/project-handoff-guide/SKILL.md) 将这一顺序作为跨会话工作入口，并限制快照规模与额外文档数量。

| 研究认识 | Agent 的具体动作 | 对应文件 |
| --- | --- | --- |
| 需求、决定、计划和现场不能互代（第一节） | 查找权威文档并明确当前快照的职责 | [snapshot-and-authority.md](../../../skills/software-engineering/project-handoff-guide/references/snapshot-and-authority.md) |
| 快照需要覆盖真实恢复要素（第二节） | 保留版本、已确认授权、验证及待办，不复制流水日志 | [snapshot-and-authority.md](../../../skills/software-engineering/project-handoff-guide/references/snapshot-and-authority.md) |
| 旧进度可能与 Git 现场冲突（第三节） | 接手先查分支、提交、工作区和测试的适用版本 | [recovery-and-exit.md](../../../skills/software-engineering/project-handoff-guide/references/recovery-and-exit.md) |
| 会话摘要不等于持久状态（第四节） | 以外部可检查资料恢复，不假定可以读取内部压缩状态 | [SKILL.md](../../../skills/software-engineering/project-handoff-guide/SKILL.md) |
| 好的交接要能继续执行（第五节） | 给出具体下一项动作与恢复条件，保护未提交工作和权限边界 | [recovery-and-exit.md](../../../skills/software-engineering/project-handoff-guide/references/recovery-and-exit.md) |

Skill 只负责跨会话状态的保存和恢复。阶段性删除或合并文档、测试及临时文件属于 `project-maintenance-guide`；实现计划与架构决策属于 `design-guide`。这使交接不会因为涉及项目文档，就扩大为对整个仓库的内容治理。
