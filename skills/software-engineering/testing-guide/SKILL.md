# 测试与需求验收（Testing Guide）

让验证真正判断软件是否符合需求，而不是让当前实现证明自己正确。

## 建立独立预期

1. 读取用户确认的行为、项目规范、相关代码与测试。先写出关键输入与预期结果；测试 oracle（正确答案依据）来自需求、领域规则、独立计算或可信基准，不能用被测实现生成 expected 值。
2. 按风险识别正常路径、重要边界、错误输入、状态变化、副作用和原始缺陷复现。需求本身不明确时指出影响，不自行替用户决定业务规则。
3. 把关键行为轻量映射为`需求 → 场景 → 预期依据 → 测试方式 → 实际证据`，小任务直接在对话中处理，不默认创建表格文件。见 [测试设计与独立预期](references/oracles-and-cases.md)。

## 执行与判断测试价值

1. 选择适合的单元/组件、集成、端到端与必要人工验收，结合可见外部行为和内部风险。Mock 隔离不可控依赖，但不能遮蔽关键真实 API、持久化与权限边界。
2. 断言要能发现具体错误结果，不只检查“无异常”“返回非空”“某函数被调用”。对于关键逻辑，按风险考虑独立评审、变异测试或故障注入；不强制全部任务 TDD。
3. 控制测试数据、随机性、时间和环境；等待应依据可观察条件，避免任意休眠。涉及生产数据或付费服务时先确认测试权限和环境。
4. 修复 Bug 时尽可能先复现原始症状，改后验证相同场景与相关回归。按变更影响逐步扩大测试；不能看到“0 退出码”就忽略实际被跳过的用例。见 [执行与验收证据](references/evidence-and-verification.md)。

## 完成说明

报告实际执行的命令/场景、结果、当前代码版本及未覆盖范围。区分实现完成、构建通过、局部测试通过和用户可观察验收通过；不将覆盖率或全部 mock 通过当作业务证明。没有环境时说明限制，不降低验收标准、不凭空声称测试成功。
