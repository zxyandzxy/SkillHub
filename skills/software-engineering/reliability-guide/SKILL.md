# 运行可靠性与故障语义

先定义发生故障后系统可承诺的状态，再选择异常、事务、重试或恢复机制。正确失败优于把部分执行包装为完整成功。

## 划定操作及失败情况

读取任务、当前调用与数据流，区分业务拒绝、临时外部故障、持续不可用、部分成功、未知完成状态和违反不变量的程序错误。识别对用户可见的影响、已产生的副作用及需要保护的资源。

## 设计安全的故障处理

1. 确定操作成功、失败与未知的语义，以及状态需要具备的原子性、持久性和恢复条件。
2. 仅在能恢复、清理资源或补充上下文的边界捕获异常；不得吞错或以宽泛回退掩盖程序缺陷。
3. 设置与任务总预算相称的超时；重试仅针对可能恢复的错误，明确次数上限、退避、抖动、取消以及上游/下游责任。
4. 对有副作用操作检查幂等键、唯一约束、状态核对或补偿方式。客户端超时并不能证明服务端未执行。
5. 降级或缓存替代应明确限制，不以过期数据或部分结果冒充完整成功；复杂熔断和隔离需要真实故障扩散风险。

故障分类及状态保护见 [failure-semantics.md](references/failure-semantics.md)，重试与验证见 [retries-and-validation.md](references/retries-and-validation.md)。

## 通过故障场景核查

按实际系统模拟连接断开、超时、重复请求、部分写入、重启、权限拒绝和资源耗尽等相关场景。检查用户反馈、持久状态、资源释放、重试上限及恢复行为，不仅检查是否抛出异常。故障注入必须在获授权的安全环境执行；不能为了验证而破坏生产数据。

## 交付及边界

说明故障类别、状态保证、采用的机制、实际核查、仍可能的未知状态与恢复步骤。重要的数据丢失取舍、费用和对外语义变更由用户决定。不为小型本地程序默认引入分布式故障框架；真实生产问题的根因调查使用 debugging-guide。
