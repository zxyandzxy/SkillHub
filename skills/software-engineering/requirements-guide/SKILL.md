# 软件需求发现与验收定义

把用户关心的实际问题转化为开发者可以实现、测试者可以判断的要求。先理解已有事实和目标，再处理会改变结果的重要分歧；不要用一份很长的假想功能清单代替真实需求。

## 调查与划定问题

1. 读取用户原话、项目说明、现有界面、接口、相关代码和已有决定；已能通过资料取得的信息不重复询问。
2. 区分可核查事实、用户目标、真实用户证据、尚未验证的假设、Agent 建议和已经确认的取舍。现有实现不自动证明当前行为符合真实需要。
3. 明确谁在什么情境下遇到什么问题、希望产生什么可观察结果。若用户提出的是具体解决方案，先判断它服务的目标及是否存在关键约束。

## 按决策依赖澄清

- 找出会改变功能、范围、业务规则、风险或验收的决定，先处理前提；每轮优先问一个最重要且可以回答的问题。
- 说明答案会影响什么，有依据时给少量具体选项和建议；不要求用户选择陌生的框架名。
- 已确认的事项不再问，低影响且可逆的实现细节可在授权范围内处理；真正影响结果的歧义保留为待决。
- 用户难以仅凭文字判断界面体验时，可建议有边界的可撤销原型。原型观察不能代替真实用户研究。

复杂访谈顺序见 [decision-interview.md](references/decision-interview.md)。

## 形成可验收的要求

- 描述目标、主要场景、范围/非目标、规则与数据含义、适用约束及重要验收条件；按实际任务缩放，不强制完整 PRD。
- 关键行为用“前提—操作—预期结果”描述，覆盖必要的错误与边界。预期应来自已确认业务规则，不根据待测实现倒推出正确答案。
- 区分产品必须满足的行为和普通实现方案；无法核实的指标或用户偏好保持待确认，不伪造使用量、延迟目标或满意度。
- 检查需求是否清楚、彼此一致、可行、可验证，并给下游测试保留独立判断依据。细节见 [acceptance-and-traceability.md](references/acceptance-and-traceability.md)。

## 收敛及边界

当目标、关键场景、范围、重大约束和验收条件足以支持下一步，且阻碍性决定已明确，就结束访谈。只获授权做需求分析时交付可审阅需求，不自动开始代码实施。需求改变时更新受影响的条件与下游工作，不以已有实现为不可变事实。

不要把所有简单任务升级成采访，也不要把技术组件数量当作需求完整程度。重大产品决策由用户确认；设计和实现属于各自专项工作。
