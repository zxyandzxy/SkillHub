# 项目资产维护（Project Maintenance）

让仓库中的长期资产有明确用途、可信来源和实际维护路径；不以文件更少作为成功标准。

## 界定维护范围并调查

1. 基于真实触发：出现相互矛盾的文档、过时命令、重复测试、失效脚本、无用生成文件或正式发布需要。限定本轮对象，不把局部修复变为整个仓库的大扫除。
2. 对候选资产核查用途、权威位置、实际引用、运行/CI/发布入口、历史价值、恢复路径和处理风险。文件年龄、名称、一次失败、静态搜索没有引用均不足以证明可删。
3. 根据资产类型分别判断文档的读者职责、测试的独立验收价值、工具的复用程度，以及生成物是否参与发布或复现。见 [文档与测试资产](references/docs-and-tests.md)。

## 处理与验证

1. 为每项选择保留、更新、合并、归档/标记替代、隔离或删除。历史重要但不再现行的记录应保留其形成原因并标记新入口；多份事实性说明应收敛到可识别的当前权威版本。
2. 删除前核查源码、配置、动态注册、CI、部署、文档链接、外部依赖、用户未提交内容和恢复路径。权限不足或用途不清时先保留，说明疑点。见 [安全迁移与清理](references/safe-migration.md)。
3. 从证据最充分且风险较低的项目开始，小批执行；每批验证相关命令、链接、测试、构建和发布入口。减少文件数但破坏实际工作流不算成功。
4. 记录处理后哪份资料是当前入口、怎样恢复历史，以及哪些资产仍需确认。不为普通清理创建永久性管理报表。

## 边界

删除、移动、公开发布或改变受依赖接口时遵守用户授权；避免覆盖他人未提交修改。普通编码产生的局部无用文件由 `clean-code-guide` 直接清理，不启动项目级资产治理。历史科研过程材料与当前运行说明有不同职责，不能为了让历史看起来一致而改写过去的记录。
