# 修复、验证与无效尝试处理

## 复现与回归

优先使原故障在可控环境稳定出现，固定测试或人工步骤。修改被支持的原因后先重跑原复现，再覆盖相关边界与防回归检查。验证结果需对应最新代码、配置和环境；不能凭以前的通过记录宣布当前修改成功。

## 缓解与根因修复

断路、重试、回退和限流可能缓解用户影响，但未必改变故障原因。临时缓解需要写明副作用、监测、恢复路径及未解决调查，不应伪装为已修复。

## 反复失败

无新证据的重复补丁应停止，回到预期、复现条件和竞争假设。多次失败并不自动意味着需要重构；只有具体耦合或状态问题被观察到时才提出架构层改变。

## 交付信息

说明症状和条件、根因及证据、实际修改、执行了哪些验证、未验证范围、剩余风险与恢复入口。对难复现问题还应保留仍有效的调查路径。来源：https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md 。
