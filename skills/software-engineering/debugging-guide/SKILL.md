# 证据驱动故障排查

将可观察故障转化为具体原因、最小修复和可重复验证。先确认发生了什么，再调查为什么发生；失败次数不能代替原因证据。

## 建立正确基线与复现

读取完整错误、目标行为、相关提交和环境信息。明确触发步骤、实际结果、正确行为的依据、出现频率和影响范围。尽量复现原始症状，再缩小输入或路径；暂不能复现时继续获取诊断证据，不猜测并直接提交大规模修改。

## 沿边界定位原因

1. 从观察到的失败点追踪输入、状态、调用与最近变化，寻找第一个偏离预期的边界。
2. 对跨组件问题检查请求、参数、配置、数据格式、状态转换与错误传播；对偶发问题核对时间、并发、资源和环境差异。
3. 将假设写成可以被否定的预测：“若 X 导致 Y，观察/实验 Z 应出现结果 R”。优先使用小而可撤销的区分性实验，一次尽量改变一个相关条件。
4. 假设被排除时撤销临时试验改动，并记录有效发现；持续重复同样失败而没有新证据时重新检查思路，不在失败补丁上累积猜测。

定位方法见 [hypothesis-and-boundaries.md](references/hypothesis-and-boundaries.md)。诊断日志不得输出密钥、令牌和不必要的个人数据。

## 修复与回归

用自动化失败测试或可重复的人工步骤记录原症状；在证据支持的原因上进行最小修改，不混入无关重构。先证明原症状消失，再按影响检查相邻行为、失败路径和项目要求的验证。清理临时诊断内容，按需保留安全且可复用的监测。说明诊断、修复、证据和未知部分，详见 [regression-and-report.md](references/regression-and-report.md)。

若只能提出超时、重试或降级缓解，须把缓解与已确认根因修复区分。未经授权不得在生产环境进行破坏性诊断或改变业务数据。

## 退出边界

已确认原因并完成相关回归时结束。根因仍不明时准确报告已排除的假设、剩余疑点和下一项有效调查，不虚称已修复。复杂系统故障排查由本 Skill 主导；面向未来故障语义的设计由 reliability-guide 处理。
