# 系统设计与实施计划（Design Guide）

依据已确认需求和实际代码建立可理解、可实现、可验证的设计。设计深度与影响范围相称。

## 确定现实条件

1. 读取当前需求、项目约定、调用入口、相关数据/测试和已确认方案。沿真实代码核对模块、调用方与数据所有权；文档与实现冲突时先说明差异。
2. 判定当前任务：小范围现有结构内修改只需说明修改位置与验证；新模块、接口或持久化边界变化需要明确职责、协议、兼容和异常；可行性未知时设计有界实验。
3. 对用户已确认的目标与方案继续执行调查和准备，仅对会改变产品含义、长期约束、兼容性或重要成本的选择请求决定。

## 形成设计

1. 检查现有能力能否满足需求；以职责及变化原因组织模块，明确谁拥有数据、谁可以写入、调用如何穿过边界，避免为假想扩展预先构建通用平台。
2. 只有实质可行方案不同且影响结果时才比较备选。说明输入输出、失败处理、性能/成本取舍、兼容与迁移，而非罗列模式名称。
3. 从一条真实用户或系统流程验证设计闭合：输入如何被校验，数据在何处处理与持久化，成功和失败如何向调用者表现。
4. 核查跨模块依赖、循环引用、公共接口变化和数据状态。只有重要且难撤销的结构性选择才维护简短 ADR；必要时采用适合项目的自动化架构边界检查。见 [架构职责与演进](references/architecture-and-decisions.md)。

## 转成可执行计划

1. 按端到端可观察成果划分增量，先打通关键路径，再补必要变体与异常；每项说明结果、受影响范围、前提、验收及集成影响。
2. 长期项目保持总体里程碑简洁，只展开近期批次。涉及多 Agent 时仅在任务、接口、修改范围及集成责任可以隔离的条件下并行。见 [增量实施与交接](references/incremental-planning.md)。
3. 若用户只要求设计，提交可审核的方案后停止，不自行实施；已授权实施则按阶段验证继续，不因每个文件变化额外请求许可。

## 完成与边界

方案应可从已确认需求回指职责、接口和真实验收；尚未确定的关键技术条件明确标记。普通编码、测试、UI 视觉设计由相应任务承担。不为简单修复强制 ADR、架构图、Git worktree、CI 或多层计划文件；不能把未运行的可行性方案写成验证通过。
