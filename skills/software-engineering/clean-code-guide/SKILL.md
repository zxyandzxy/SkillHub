# 可维护代码与局部实现（Clean Code Guide）

在满足真实需求的前提下，以最容易理解和继续维护的方式完成必要修改。

## 动手前识别范围

- 读取用户目标、项目约定、当前代码、主要调用方和相关测试。区分本次要求、为正确性必须进行的连带变更与任务外问题。
- 以项目现有接口和结构为起点，不把个人风格偏好当成重构理由；若新事实涉及产品行为或重要兼容取舍，说明影响后请用户决策。

## 编码与整理

1. 使用足以解决当前需求的简单实现，不为没有证据的未来功能创建大量配置开关、抽象层或备用路径。简洁不等于牺牲关键校验、必要错误处理和可理解的职责边界。
2. 让每项改动都能解释它如何服务目标：相关代码、必要测试及受影响说明可以同时修改；与需求无关的命名、格式化和整理分开处理。见 [范围、抽象与失败边界](references/scope-and-simplicity.md)。
3. 根据现有职责和变化原因决定是否拆分模块。长函数、`utils` 目录和代码重复是调查线索，不是固定行数或目录规则下的自动重构命令。
4. 注释说明非显然理由、协议约束、不变量、单位和副作用；不逐行复述代码。实现改变时核对注释、接口和文档是否过期。见 [注释、结构与安全清理](references/comments-and-cleanup.md)。
5. 清理由本次变更产生且已确认无用的临时文件、import、依赖或旧分支。对于仓库其他部分的遗留内容，除非用户已授权对应维护范围，否则只说明问题。

## 自查和交付

完成后检查完整 diff 与工作区状态，确认不覆盖用户未提交的修改；核对调用方、必要边界输入、外部依赖和功能验证，报告实际执行的检查与未验证范围。

代码“看起来简洁”不能代替正确性与测试；已有实现清楚准确时不应为了风格进行机械重写。正式测试由 `testing-guide` 主导，全仓文档与资产生命周期由 `project-maintenance-guide` 处理。
