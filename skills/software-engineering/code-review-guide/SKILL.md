# 代码评审与反馈核查（Code Review Guide）

以需求符合度和工程可靠性两个角度检查真实代码变更，给出可定位、可验证的发现。

## 确定真正的评审范围

1. 读取用户指定的 PR、分支、提交或工作区范围和需求约束，检查 Git 分支、共同祖先、暂存、未暂存及未跟踪文件。不要用单一 `git diff HEAD` 假称已经覆盖所有变化。
2. 只有当前代码而没有基准时，只能评审当前状态；差异不存在或权限不足时如实说明，不编造问题。
3. 对变更影响的调用方、接口、测试和配置作必要上下文检查，避免仅看孤立 Diff 行。

## 两个评审视角

1. **需求符合度**：是否解决了原本问题、遗漏哪个验收场景、引入未要求的行为、破坏兼容或改变产品规则。缺少需求依据时明确此视角的限制。
2. **工程质量**：结合真实数据流和修改范围检查功能正确性、失败状态、资源处理、状态一致性、权限、性能和可维护性。复杂命名和长函数只是调查线索；自动格式规则交给已有工具。
3. 对关键风险结合相关测试和结果证据检查，必要时采取受授权的针对性验证；无真实运行证据时不能把静态阅读结果写成验收通过。见 [需求与工程风险评审](references/review-lenses.md)。

## 输出可操作发现

- 每条发现给出具体文件/位置、触发条件、预期与实际差异或证据缺口、影响和最小可行修复方向。
- 优先排序会导致错误行为、数据损坏、越权或阻塞交付的问题，合并重复项。不用表面问题数量衡量评审质量。
- 结尾交代审查范围、实际执行的检查和未覆盖部分；没有发现问题就如实说明，不能据此保证整个系统无缺陷。

## 处理他人的评审意见

先依据当前代码与需求核实，再判断接受、拒绝或澄清；不要因为评论来自另一个 Agent 就盲从，也不要为维护原方案忽略有证据的反馈。详见 [反馈核查与交付边界](references/feedback-and-delivery.md)。用户只要求 Review 时不修改文件、不回帖、不合并，也不自动产生部署授权。
