# UI/UX 设计与真实页面迭代

从用户需要完成的任务出发设计信息、操作和反馈，沿用现有设计系统并实际检查界面行为。视觉美观、功能正确和真实用户可用性需要分别判断。

## 理解任务及现有约定

确认目标用户、使用环境、任务入口、主要操作和完成结果。优先检查现有界面、设计系统、组件和平台规范，确定是否已有可复用的字体、颜色、间距与交互状态；不因个人偏好重建风格。

## 设计流程、层级和状态

1. 说明用户在每一步需要看到什么、作出什么判断、完成后得到什么反馈；先安排信息与操作顺序，再选择卡片、菜单或弹窗等组件。
2. 用排版、对齐、留白、语义色及清楚标题构建层级，保持同类控件和状态一致；必要时才引入少量语义化设计 token。
3. 按真实功能覆盖初始、空、加载、处理中、成功、错误、禁用、无权限、长内容、窄屏和输入设备状态；不只实现默认静态截图。
4. 界面文案说明可理解的操作与结果，错误提示说明下一步，避免暴露内部错误码和技术字段。

任务结构和实际状态清单见 [tasks-and-states.md](references/tasks-and-states.md)。

## 无障碍与实际检查

使用语义控件、可见焦点、键盘/触摸支持、足够对比及不只依赖颜色的信号；按目标平台与适用规范判断。尽可能运行真实页面，在代表设备、尺寸和状态中操作，检查溢出、遮挡、滚动、反馈和恢复。细节见 [accessibility-and-evidence.md](references/accessibility-and-evidence.md)。

静态截图只证明某个时刻的视觉状态；启发式审查不等于真实用户测试。若缺少运行环境或用户研究，如实交代已检查与未验证的内容。

## 范围与交付

交付被修改的用户流程、界面与可复核的检查结果。只修改用户要求的范围，不给后端小改动强制增加完整 UI 设计流程。重大产品目标与数据规则由 requirements-guide 确认；模块接口和架构由 design-guide 负责。
