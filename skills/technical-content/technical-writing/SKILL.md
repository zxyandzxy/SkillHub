# 技术写作（Technical Writing）

以读者需要回答的问题组织事实与解释，保持专业准确性、技术深度和自然表达。

## 判断当前任务

- 确认读者、写作用途、熟悉程度、材料来源、语言、现有稿件和需要修改的范围。已有资料中能查到的事实不重复询问。
- **新建解释/教程**：先确定读者的实际问题与知识依赖，再选择一个可贯穿全文的具体例子；参考 [概念解释与教学文章](references/explanation-and-sequence.md)。
- **技术综述**：先明确要比较的问题和维度，以任务、机制、适用条件和证据组织现有方法，不逐篇摘要。
- **论文转博客/报告**：先核对论文原文、数据、图号、方法假设及允许的结论，按新读者重排叙事，不逐段删减论文；参考 [编辑与跨媒介保持](references/editorial-and-evidence.md)。
- **局部修订**：只修改已提出的问题及必要衔接。原句信息正确、读者可懂时保持不变。

## 构造文章

1. 先写清读者读完应能解释或完成什么。把必要先备概念按依赖关系排列；使用某个术语或符号前给出足够定义。
2. 选择能揭示机制的例子，记录输入、操作、状态变化和结果。对抽象规则，说明例子怎样推广；对玩具例子，明确其演示性，不把它当作实验验证。
3. 每一节承担一个读者问题，每段交代事实、理由或实例中的新信息。相邻段落用真正的因果、条件、对比或推导连接，不用空泛过渡。
4. 在图、表、代码及正文之间统一变量、名称、单位和方向。可复用原图时核查来源与许可；需要重画则保持原数据和科学关系。
5. 区分“作者原文报告”“能够核对的技术事实”“本次解释性推断”。用必要的限定词防止把局部结果写成通用规律。
6. 内容遍检查技术定义、逻辑依赖、证据与反例；语言遍检查主语、动作、冗余句、术语一致性和阅读节奏。表达质量不能代替证据。

## 交付和边界

直接交付用户请求的正文或实际文件，不默认创建文章提纲、研究日志和编辑报告。修改稿需核对事实与来源、数字、比较条件、因果强度和受影响的引用。遇到未提供的重要信息，指出缺口或使用明确标记的占位符。

简短问答不强制使用完整文章工作流；文献证据不足可按需使用 `literature-research`。需投稿论文章节时使用 `academic-writing`。已达到读者目标、内容准确且不再存在有意义的局部改进时停止，不为显示产出而继续重写。
